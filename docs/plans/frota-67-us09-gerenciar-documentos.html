1. Contexto, Objetivo e Escopo

1.1 Objetivo

O Gestor de Frota da FSPH passa a cadastrar, corrigir, renovar e anular os documentos obrigatórios de cada veículo (CRLV, licenciamento, IPVA, seguro, contrato de locação e outros) e a ser avisado dos documentos vencidos ou que vencem dentro do prazo de alerta — uma das principais dores do Gestor, pois veículo com documento vencido não pode circular em transporte institucional nem em remoções do SVO.

Exemplo de uso real: "O gestor recebe o CRLV 2027 da van VAN-0A00 e registra a renovação; o CRLV 2026 deixa de aparecer no alerta, mas continua no histórico do veículo."

1.2 Escopo desta entrega (confirmado)

EntraFica fora (YAGNI / outra subtarefa)
  • BE (FROTA-69): API /vehicle-documents com listagem filtrada, consulta individual com linha do tempo, cadastro (inclui renovação), correção (PUT), anulação justificada e consulta de documentos a vencer.
  • Cálculo da situação no Service e prazo de alerta configurável (env + query param).
  • Eventos append-only em fleet.vehicle_document_events e trilha em audit.logs.
  • QA (FROTA-167): testes unitários do service e integração HTTP + PostgreSQL.
  • Tela React (FROTA-70) — com outro desenvolvedor; este plano entrega apenas o contrato de handoff (seção 6).
  • Upload/anexo de arquivo do documento (attachment_url permanece nulo).
  • Notificação ativa (e-mail/push) e consumo pelo dashboard (US21).
  • Paginação da listagem (paridade com /maintenance-orders).
  • Migrations: a estrutura já existe (FROTA-68).

2. Requisitos e Regras de Negócio (Casos de Borda)

2.1 Situação do documento (calculada no Service, nunca persistida)

Referências: hoje = currentFsphDate() (fuso America/Maceio) e limite = hoje + alertDays. Intervalo inclusivo, idêntico à regra de CNH já usada em motoristas.

Ordem de avaliaçãoCondiçãostatusRótulo sugerido ao FEEntra em /expiring?
1isAnnulled = trueANNULLEDAnuladoNão
2Existe documento não anulado com supersedes_id = idRENEWEDRenovadoNão
3expiresAt < hojeEXPIREDVencidoSim (se veículo ≠ INACTIVE)
4hoje ≤ expiresAt ≤ limiteEXPIRINGA vencerSim (se veículo ≠ INACTIVE)
5expiresAt > limiteVALIDVálidoNão

daysUntilExpiration = dias corridos entre hoje e expiresAt (negativo quando vencido), devolvido para o FE não reimplementar regra de data.

2.2 Ciclo de vida (eventos em fleet.vehicle_document_events)

POST (sem supersedesId) ──► REGISTERED ──► [vigente] ──PUT──► UPDATED (n vezes)
POST (supersedesId = A) ──► RENEWED (no novo doc) ──► A passa a status RENEWED
PATCH /:id/annul        ──► ANNULLED (terminal: não aceita PUT, annul nem renovação)
Anular a renovação R de A ──► A volta a ser vigente (D12)
RECTIFIED: valor existente no CHECK, não utilizado nesta US (D4).

2.4 Requisitos não-funcionais

  • Atomicidade: toda mutação roda em vehiclesRepository.withTransaction, travando primeiro o veículo (FOR UPDATE) e depois o documento — mesma ordem global de locks de manutenções, evitando deadlock.
  • Idempotência: reenvio do mesmo cadastro converge para 409 (D9) sob o lock do veículo; renovações concorrentes do mesmo A são serializadas pelo mesmo lock (a segunda recebe 409 C10).
  • Performance: /expiring usa o índice parcial fleet_vehicle_documents_by_expiration; detecção de superado usa fleet_vehicle_documents_by_supersedes; filtros com predicados sargáveis (sem função sobre coluna).
  • Mensagens: erros em português, no campo erro, dizendo o problema e o próximo passo (WCAG 3.3.1 / 3.3.3 — lidas pelo FE).
  • Preservação histórica: nenhum DELETE; anulação é flag + evento; eventos são append-only (trigger existente).

4.3 Consultas-chave (esboço — o implementador mantém projeções explícitas)

-- Projeção base reutilizada por findById / list / listExpiring (sem SELECT *)
SELECT d.id::text AS id, d.vehicle_id::text AS "vehicleId",
       v.license_plate AS "licensePlate", v.model, v.status AS "vehicleStatus",
       d.document_type AS "documentType", d.document_number AS "documentNumber",
       d.issued_at::text AS "issuedAt", d.expires_at::text AS "expiresAt", d.notes,
       d.supersedes_id::text AS "supersedesId", s.id::text AS "supersededById",
       d.is_annulled AS "isAnnulled", d.annulment_reason AS "annulmentReason",
       d.vehicle_snapshot AS "vehicleSnapshot", d.created_by::text AS "createdBy",
       d.revision, d.created_at AS "createdAt", d.updated_at AS "updatedAt"
  FROM fleet.vehicle_documents d
  JOIN fleet.vehicles v ON v.id = d.vehicle_id
  LEFT JOIN LATERAL (
        SELECT n.id FROM fleet.vehicle_documents n
         WHERE n.supersedes_id = d.id AND n.is_annulled = false
         ORDER BY n.id DESC LIMIT 1) s ON true

-- list(criteria): filtros traduzidos pelo service (regra de situação mora no service)
 WHERE ($1::bigint IS NULL OR d.vehicle_id = $1)
   AND ($2::text   IS NULL OR d.document_type = $2)
   AND ($3::boolean IS NULL OR d.is_annulled = $3)
   AND ($4::boolean IS NULL OR (s.id IS NOT NULL) = $4)      -- superado?
   AND ($5::date   IS NULL OR d.expires_at >= $5)
   AND ($6::date   IS NULL OR d.expires_at <= $6)
 ORDER BY d.expires_at ASC, d.id ASC

-- listExpiring(limitDate): vigentes de veículos ativos com vencimento <= limite
 WHERE d.is_annulled = false AND s.id IS NULL
   AND v.status <> 'INACTIVE' AND d.expires_at <= $1
 ORDER BY d.expires_at ASC, d.id ASC

-- Duplicidade (D9), executada após travar o veículo
SELECT EXISTS (SELECT 1 FROM fleet.vehicle_documents
                WHERE vehicle_id = $1 AND document_type = $2 AND expires_at = $3
                  AND is_annulled = false AND ($4::bigint IS NULL OR id <> $4)) AS found

-- Trava do documento (após a do veículo)
SELECT id FROM fleet.vehicle_documents WHERE id = $1 FOR UPDATE

}

Validações (400, antes de abrir transação): validateId (texto numérico positivo ≤ BIGINT), tipo ∈ VEHICLE_DOCUMENT_TYPES, datas via isValidIsoDate, issuedAt ≤ hoje, expiresAt ≥ issuedAt, notes obrigatório em OTHER, reportedBy/reason não vazios, expectedRevision inteiro positivo, days inteiro 1–365, filtros válidos. Corpo não-objeto → 400 (no controller).
  2. create: withTransaction → findByIdForUpdate(vehicleId) (404) → se supersedesId: lockById (404), mesmo veículo/tipo (409 C09), não anulado e sem supersededById (409 C10) → existsDuplicate (409 C07) → findActorSnapshot (401) → repository.create → evento REGISTERED ou RENEWED → audit.recordAudit com operation = eventType, table = 'fleet.vehicle_documents'.
  3. updateDocument: rejeita vehicleId/documentType/supersedesId no corpo (400 C14) → lê o documento (404) → transação: trava veículo, depois documento → anulado (409 C15) → revisão diferente (409 C13) → mescla { ...before, ...input } e revalida → se expiresAt mudou, existsDuplicate excluindo o próprio id → saveAttributes → evento UPDATED (before/after) → auditoria.
  4. annul: mesma abertura de update → anulado (409) → revisão (409) → supersededById presente (409 C18) → repository.annul(id, reason) → evento ANNULLED → auditoria. Nenhuma alteração no documento anterior: ele volta a vigente por derivação (D12).
  5. Leitura: list traduz status em critérios (4.4); listExpiring usa limitDate = hoje + (days ?? alertDays); ambos devolvem { referenceDate, alertDays, items } com status e daysUntilExpiration calculados por resolveVehicleDocumentStatus. Em /expiring, alertDays reflete o days efetivamente usado.
  6. Erros de domínio sempre VehicleDocumentServiceError; CHECK violado inesperadamente (23514) não é mascarado (vai ao handler global → 500), pois indica falha de validação no service.

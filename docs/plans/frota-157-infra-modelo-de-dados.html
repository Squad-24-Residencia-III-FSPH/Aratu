1. Contexto, Objetivo e Escopo

1.1 Contexto Operacional (FSPH / SVO)

O Sistema Aratu sustenta a gestão operacional da frota institucional da Fundação de Saúde Parreiras Horta (FSPH) e as operações prioritárias de remoção cadavérica do Serviço de Verificação de Óbito (SVO). Para que as histórias do Épico E02 (US04 — Veículos, US05 — Motoristas e US06 — Tipos de Serviço e Compatibilidade) funcionem com integridade relacional, concorrência otimista (revision) e preservação histórica imutável (SCD Tipo 4 / Append-Only), o schema nativo fleet no PostgreSQL 18 precisa prover todas as tabelas, constraints declarativas, índices sargáveis e dados iniciais de homologação.

1.2 Objetivo da Tarefa

Concluir integralmente o modelo relacional do schema fleet no PostgreSQL 18 executando na ordem das três subtarefas da FROTA-157:

  1. FROTA-42 — Evolução compatível de fleet.vehicles e sincronização da camada de Veículos: A migration base 202610210001_create_vehicles.sql já está ativa na branch develop atendendo às APIs de FROTA-43 e FROTA-45. Será criada uma migration complementar adicionando as colunas descritivas previstas na FROTA-42/FROTA-46 (brand, model, year, vehicle_type e ownership) com valores opcionais/default seguros, atualizando o índice único fleet_vehicles_license_plate_unique para expressão case-insensitive upper(license_plate) e adaptando vehicle.types.ts, vehicles.repository.ts e vehicles.service.ts para projetar, validar e persistir essas colunas e buscar placas com upper(license_plate) = upper($1).
  2. FROTA-48 — Criação de fleet.drivers e fleet.driver_events: Criar a tabela de condutores (name, cpf, cnh_number, cnh_category, cnh_expires_at, phone, status, user_id opcional para auth.users, revision, created_at, updated_at) sem vínculo fixo com veículo, acompanhada da tabela histórica imutável fleet.driver_events com trigger de bloqueio contra UPDATE/DELETE (padrão SCD Tipo 4 idêntico a fleet.vehicle_events).
  3. FROTA-165 — Criação de fleet.services e fleet.vehicle_services: Criar o catálogo de tipos de serviço unificando os atributos da FROTA-165 e de docs/manuais/padroes-codigo.md (name com unicidade em lower(name), description, categories, requires_triage, requires_weight, requires_identification, active, revision, created_at, updated_at) e a tabela associativa fleet.vehicle_services (id, vehicle_id, service_id, created_at) com constraint UNIQUE (vehicle_id, service_id) e índices nas duas FKs.
  4. Provisionamento Idempotente (npm run db:seed): Estender backend/src/database/scripts/seed.ts com a função idempotente seedInitialFleet(pool) para popular exemplos fictícios de homologação (incluindo as três caminhonetes S10 do SVO sugeridas na issue, tipos de serviço iniciais e seus respectivos vínculos em fleet.vehicle_services).

2. Requisitos e Regras de Negócio (Casos de Borda)

2.1 Requisitos Funcionais (RF)

  • RF01 (Complemento de fleet.vehicles — FROTA-42):
    • Adicionar em fleet.vehicles as colunas brand TEXT, model TEXT, year INTEGER, vehicle_type TEXT e ownership TEXT NOT NULL DEFAULT 'OWNED';
    • Aplicar constraints declarativas: year IS NULL OR (year >= 1980 AND year <= 2100) e ownership IN ('OWNED', 'LEASED');
    • Recriar o índice fleet_vehicles_license_plate_unique sobre a expressão (upper(license_plate)), bloqueando duplicidades independentemente de caixa alta/baixa (ex.: abc1d23 vs ABC1D23) mesmo em inserções diretas no banco;
    • Relaxar a constraint de formato fleet_vehicles_license_plate_format para avaliar upper(license_plate) ~ '^[A-Z]{3}([0-9]{4}|[0-9][A-Z][0-9]{2})$', permitindo que o índice único case-insensitive seja exercitado e testado diretamente no PostgreSQL 18.
  • RF02 (Tabela fleet.drivers e Histórico fleet.driver_events — FROTA-48):
    • Criar fleet.drivers com id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name TEXT NOT NULL, cpf TEXT NOT NULL (exatamente 11 dígitos numéricos ^[0-9]{11}$), cnh_number TEXT NOT NULL, cnh_category TEXT NOT NULL (valores permitidos: 'A', 'B', 'C', 'D', 'E', 'AB', 'AC', 'AD', 'AE'), cnh_expires_at DATE NOT NULL, phone TEXT, status TEXT NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE', 'INACTIVE', 'AWAY')), user_id BIGINT REFERENCES auth.users(id) ON DELETE RESTRICT (opcional), revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0), created_at TIMESTAMPTZ e updated_at TIMESTAMPTZ;
    • Não criar coluna de veículo em fleet.drivers (o vínculo motorista × veículo ocorre por viagem/escala, nunca de forma fixa no cadastro);
    • Criar índice único fleet_drivers_cpf_unique ON fleet.drivers (cpf) e índice único parcial fleet_drivers_user_id_unique ON fleet.drivers (user_id) WHERE user_id IS NOT NULL;
    • Criar tabela histórica append-only fleet.driver_events (com FK driver_id REFERENCES fleet.drivers(id) ON DELETE RESTRICT, event_type IN ('CREATED', 'UPDATED', 'STATUS_CHANGED'), occurred_at, registered_at, reported_by, registered_by REFERENCES auth.users(id) ON DELETE RESTRICT, actor_snapshot JSONB, reason, before_state JSONB, after_state JSONB) protegida por trigger fleet_driver_events_append_only.
  • RF03 (Tabelas fleet.services e fleet.vehicle_services — FROTA-165):
    • Criar fleet.services com id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name TEXT NOT NULL (não vazio), description TEXT, categories TEXT[] NOT NULL DEFAULT ARRAY['PASSENGER']::TEXT[] (subconjunto válido de PASSENGER, BODY, OTHER), requires_triage BOOLEAN NOT NULL DEFAULT false, requires_weight BOOLEAN NOT NULL DEFAULT false, requires_identification BOOLEAN NOT NULL DEFAULT false, active BOOLEAN NOT NULL DEFAULT true, revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0), created_at TIMESTAMPTZ e updated_at TIMESTAMPTZ;
    • Criar índice único case-insensitive fleet_services_name_lower_unique ON fleet.services (lower(btrim(name)));
    • Criar fleet.vehicle_services com id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, vehicle_id BIGINT NOT NULL REFERENCES fleet.vehicles(id) ON DELETE RESTRICT, service_id BIGINT NOT NULL REFERENCES fleet.services(id) ON DELETE RESTRICT e created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp();
    • Garantir unicidade do par com CONSTRAINT fleet_vehicle_services_pair_unique UNIQUE (vehicle_id, service_id) e índices nas duas FKs (fleet_vehicle_services_by_vehicle e fleet_vehicle_services_by_service).
  • RF04 (Seed Inicial Idempotente da Frota — npm run db:seed):
    • Adicionar em backend/src/database/scripts/seed.ts a função exportada seedInitialFleet(pool: Pool) executada após o seed do Administrador inicial;
    • Inserir de forma idempotente (ON CONFLICT DO NOTHING) as três caminhonetes S10 do SVO com placas Mercosul fictícias (ex.: SVO1A01, SVO1A02, SVO1A03, marca Chevrolet, modelo S10, operation_type = 'SVO', categories = ARRAY['BODY'], seats = 2, body_limit = 2), acompanhadas de seus eventos iniciais CREATED em fleet.vehicle_events e dos tipos de serviço base (Remoção Cadavérica SVO, Transporte Institucional de Passageiros, Transporte de Amostras e Insumos) e respectivos vínculos em fleet.vehicle_services.

2.2 Cenários de Negócio e Casos de Borda (Dado / Quando / Então)

  • Cenário 1 — Unicidade case-insensitive de placa em fleet.vehicles (FROTA-42):
    Dado que existe um veículo cadastrado com placa ABC1D23,
    Quando uma instrução SQL tenta inserir outro veículo com placa abc1d23,
    Então o PostgreSQL 18 rejeita a operação com erro de violação de unicidade (SQLSTATE 23505) no índice fleet_vehicles_license_plate_unique.
  • Cenário 2 — Compatibilidade retroativa com VehiclesRepository (FROTA-43/45):
    Dado que o VehiclesRepository.create() atual insere apenas (license_plate, categories, seats, body_limit, weight_limit, operation_type, status),
    Quando um veículo é criado pela API existente sem informar brand, model, year, vehicle_type ou ownership,
    Então o registro é gravado com sucesso assumindo ownership = 'OWNED' e NULL nas demais colunas opcionais, mantendo todos os testes de vehicles.service.test.ts passando.
  • Cenário 3 — Unicidade de CPF e vínculo opcional user_id em fleet.drivers (FROTA-48):
    Dado que existe um motorista com CPF 12345678901 e user_id = NULL,
    Quando se tenta inserir outro motorista com o mesmo CPF 12345678901, Então falha com 23505 em fleet_drivers_cpf_unique;
    E quando se insere um segundo motorista com outro CPF (98765432100) e também user_id = NULL, Então a inserção é aceita (múltiplos motoristas sem conta de usuário), mas vincular o mesmo user_id preenchido a dois motoristas falha com 23505 em fleet_drivers_user_id_unique.
  • Cenário 4 — Imutabilidade de fleet.driver_events (Append-Only):
    Dado um evento registrado em fleet.driver_events,
    Quando qualquer comando UPDATE ou DELETE é executado contra a linha,
    Então a trigger fleet_driver_events_append_only aborta a operação lançando exceção fleet.driver_events is append-only.
  • Cenário 5 — Unicidade de Tipo de Serviço e Par Veículo × Serviço (FROTA-165):
    Dado o serviço Remoção Cadavérica SVO cadastrado em fleet.services e vinculado ao veículo V1 em fleet.vehicle_services,
    Quando se tenta inserir remoção cadavérica svo (em minúsculas) em fleet.services ou repetir o par (V1, S1) em fleet.vehicle_services,
    Então o banco bloqueia ambas as duplicações com SQLSTATE 23505.
  • Cenário 6 — Reversibilidade limpa via Rollback (.down.sql):
    Dado que as migrações 202610280001, 202610280002 e 202610280003 foram aplicadas,
    Quando seus respectivos arquivos .down.sql são executados em ordem reversa e as migrações são reaplicadas,
    Então o banco retorna ao estado anterior sem resíduos e reaplica todo o schema sem erros.

4.2 Migration 2 — Motoristas e Histórico de Eventos (FROTA-48)

Arquivo: backend/src/database/migrations/202610280002_create_drivers.sql

BEGIN;

CREATE SCHEMA IF NOT EXISTS fleet;

CREATE TABLE fleet.drivers (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL CHECK (btrim(name) <> ''),
  cpf TEXT NOT NULL,
  cnh_number TEXT NOT NULL CHECK (btrim(cnh_number) <> ''),
  cnh_category TEXT NOT NULL
    CHECK (cnh_category IN ('A', 'B', 'C', 'D', 'E', 'AB', 'AC', 'AD', 'AE')),
  cnh_expires_at DATE NOT NULL,
  phone TEXT CHECK (phone IS NULL OR btrim(phone) <> ''),
  status TEXT NOT NULL DEFAULT 'ACTIVE'
    CHECK (status IN ('ACTIVE', 'INACTIVE', 'AWAY')),
  user_id BIGINT REFERENCES auth.users (id) ON DELETE RESTRICT,
  revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  CONSTRAINT fleet_drivers_cpf_format
    CHECK (cpf ~ '^[0-9]{11}$')
);

CREATE UNIQUE INDEX fleet_drivers_cpf_unique
  ON fleet.drivers (cpf);

CREATE UNIQUE INDEX fleet_drivers_user_id_unique
  ON fleet.drivers (user_id)
  WHERE user_id IS NOT NULL;

CREATE INDEX fleet_drivers_by_status_name
  ON fleet.drivers (status, name, id);

CREATE TABLE fleet.driver_events (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  driver_id BIGINT NOT NULL REFERENCES fleet.drivers (id) ON DELETE RESTRICT,
  event_type TEXT NOT NULL CHECK (event_type IN ('CREATED', 'UPDATED', 'STATUS_CHANGED')),
  occurred_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  registered_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  reported_by TEXT NOT NULL CHECK (btrim(reported_by) <> ''),
  registered_by BIGINT NOT NULL REFERENCES auth.users (id) ON DELETE RESTRICT,
  actor_snapshot JSONB NOT NULL,
  reason TEXT NOT NULL CHECK (btrim(reason) <> ''),
  before_state JSONB,
  after_state JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE INDEX fleet_driver_events_by_driver
  ON fleet.driver_events (driver_id, occurred_at DESC, id DESC);

CREATE FUNCTION fleet.prevent_driver_event_mutation()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
  RAISE EXCEPTION 'fleet.driver_events is append-only';
END;
$$;

CREATE TRIGGER fleet_driver_events_append_only
  BEFORE UPDATE OR DELETE ON fleet.driver_events
  FOR EACH ROW EXECUTE FUNCTION fleet.prevent_driver_event_mutation();

COMMIT;

Rollback: backend/src/database/migrations/202610280002_create_drivers.down.sql

BEGIN;

DROP TABLE IF EXISTS fleet.driver_events;
DROP FUNCTION IF EXISTS fleet.prevent_driver_event_mutation();

4.3 Migration 3 — Tipos de Serviço e Compatibilidade Veículo × Serviço (FROTA-165)

Arquivo: backend/src/database/migrations/202610280003_create_services.sql

BEGIN;

CREATE SCHEMA IF NOT EXISTS fleet;

CREATE TABLE fleet.services (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL CHECK (btrim(name) <> ''),
  description TEXT CHECK (description IS NULL OR btrim(description) <> ''),
  categories TEXT[] NOT NULL DEFAULT ARRAY['PASSENGER']::TEXT[],
  requires_triage BOOLEAN NOT NULL DEFAULT false,
  requires_weight BOOLEAN NOT NULL DEFAULT false,
  requires_identification BOOLEAN NOT NULL DEFAULT false,
  active BOOLEAN NOT NULL DEFAULT true,
  revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  CONSTRAINT fleet_services_categories_valid
    CHECK (cardinality(categories) > 0 AND categories <@ ARRAY['PASSENGER', 'BODY', 'OTHER']::TEXT[])
);

CREATE UNIQUE INDEX fleet_services_name_lower_unique
  ON fleet.services (lower(btrim(name)));

CREATE INDEX fleet_services_by_active_name
  ON fleet.services (active, name, id);

CREATE TABLE fleet.vehicle_services (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  vehicle_id BIGINT NOT NULL REFERENCES fleet.vehicles (id) ON DELETE RESTRICT,
  service_id BIGINT NOT NULL REFERENCES fleet.services (id) ON DELETE RESTRICT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  CONSTRAINT fleet_vehicle_services_pair_unique
    UNIQUE (vehicle_id, service_id)

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

1. Contexto, Objetivo e Escopo

No ecossistema de saúde pública e verificação de óbito da Fundação de Saúde Parreiras Horta (FSPH) e do Serviço de Verificação de Óbito (SVO), a robustez e a integridade das APIs do Sistema Aratu são vitais para a operação ininterrupta de frotas, transporte de bolsas de sangue, reagentes laboratoriais e remoção cadavérica sigilosa. Falhas de concorrência, regressões em regras de negócio ou inconsistências no banco de dados têm impacto direto no atendimento à população sergipana.

Esta tarefa (FROTA-161 — [QA] Configurar testes automatizados da API, pertencente ao épico de infraestrutura FROTA-154) estabelece a base técnica oficial de testes automatizados do backend, atendendo a um pré-requisito mandatório e bloqueante para o desenvolvimento das histórias de usuário US02 (FROTA-29 — Gerenciar usuários) e US03 (FROTA-35 — Gerenciar perfis e permissões).

Delimitação de Escopo (YAGNI)

Entra no Escopo (FROTA-161) Fora do Escopo (YAGNI)
  • Padronização do Test Runner: Formalização e estruturação do runner nativo do Node.js (node:test e node:assert/strict via tsx --test), mantendo a suíte leve, rápida e sem dependências externas pesadas (alinhado a KISS e YAGNI).
  • Banco de Dados de Teste Separado: Configuração de banco de dados isolado (aratu_test ou ${POSTGRES_DB}_test) no mesmo PostgreSQL 18 em Docker, apontado pela variável DATABASE_URL_TEST no .env e .env.example, garantindo que execuções de testes nunca alterem ou corrompam dados de desenvolvimento ou produção.
  • Mecanismo de Migrações em TypeScript: Utilitário backend/src/database/migrator.ts que lê e executa ordenadamente todas as migrações SQL (src/database/migrations/*.sql) em transações atômicas seguras.
  • Helper de Testes com PostgreSQL: Utilitário backend/tests/helpers/db-test.ts com funções para provisionar banco, rodar migrações, fornecer pool com encerramento limpo (evitando conexões presas) e executar limpeza de dados rápida (TRUNCATE ... CASCADE).
  • Scripts Padronizados no package.json: Refinamento do npm test e adição de comandos específicos (npm run test:unit, npm run test:integration, npm run test:db:setup).
  • Integração Contínua (CI): Atualização do workflow .github/workflows/ci-cd.yml adicionando container de serviço postgres:18-alpine com healthcheck no job backend-ci, garantindo que o GitHub Actions rode a suíte completa com banco real a cada Pull Request.
  • Bateria de Testes de Integração de Base: Implementação de backend/tests/database.integration.test.ts validando o funcionamento dos repositórios existentes (UsersRepository em auth.users e AuditRepository em audit.logs) diretamente no PostgreSQL 18 real.
  • Implementação de rotas ou regras de negócio novas das US02/US03 (ex.: GET /users, POST /users, GET /profiles — essas possuem tarefas próprias no Jira).
  • Testes de interface web ou componentes do frontend React 19 (escopo de tarefas de frontend).
  • Adoção de frameworks de teste externos pesados (Jest, Vitest, Cypress, Mocha) que adicionem complexidade desnecessária.
  • Criação de novos schemas ou tabelas de negócio não existentes no momento.

Decisões Confirmadas pela Regra da Dúvida

  1. Ferramenta de Testes Backend: Manter e formalizar o test runner nativo do Node.js (node:test e node:assert/strict) executado via tsx --test, que já é suportado nativamente pelo Node 24 do CI e elimina dependências transitivas.
  2. Estratégia do Banco de Testes: Mesma instância do PostgreSQL 18 em Docker (serviço db na porta 5432), com banco de dados isolado denominado aratu_test (configurável via DATABASE_URL_TEST no .env), evitando a sobrecarga de memória de múltiplos containers.
  3. Branch Criada a partir da main com Arquitetura Desacoplada: Conforme definição explícita do desenvolvedor, a branch feat/qa-configurar-testes-automatizados é criada a partir da main e mantém o conteúdo da main sem mesclar a develop neste momento. A infraestrutura de testes é desenhada de forma dinâmica e desacoplada, pronta para suportar tanto o estado atual quanto as migrações e tabelas da develop (como auth.users e audit.logs) quando for integrada.
  4. Gerenciamento Dinâmico de Migrações e Isolamento: Criação do helper backend/tests/helpers/db-test.ts e do migrator backend/src/database/migrator.ts que descobre e aplica dinamicamente todas as migrações SQL presentes no diretório migrations/ em ordem cronológica, e limpa as tabelas existentes de forma dinâmica e segura antes de cada teste de integração.
  5. Pipeline de CI (.github/workflows/ci-cd.yml): Inclusão de container de serviço postgres:18-alpine no job backend-ci, permitindo que o npm test execute testes unitários e de integração com banco de dados real em ambiente de CI automatizado.

2. Requisitos e Regras de Negócio (Casos de Borda)

Requisitos Funcionais (RF)

  • RF01 — Test Runner Padronizado: A suíte de testes deve rodar via npm test utilizando o runner nativo node:test com assertivas estritas (node:assert/strict) e execução TypeScript via tsx --test.
  • RF02 — Configuração do Banco de Testes: O ambiente de testes deve carregar as variáveis de conexão com prioridade para DATABASE_URL_TEST ou derivar da conexão padrão adicionando o sufixo _test (ex.: aratu_test), nunca apontando para o banco de desenvolvimento.
  • RF03 — Provisionamento e Migrações Automáticas: O utilitário DatabaseMigrator (backend/src/database/migrator.ts) deve escanear backend/src/database/migrations/*.sql (desconsiderando arquivos *.down.sql), ordená-los alfabeticamente/cronologicamente e aplicá-los de forma transacional e idempotente.
  • RF04 — Helper de Ciclo de Vida do Banco (db-test.ts): O helper de teste deve expor:
    • setupTestDatabase(): Assegura a criação do banco de teste caso não exista e aplica todas as migrações pendentes;
    • truncateTestDatabase(): Limpa dados de todas as tabelas dos schemas auth e audit preservando a estrutura e reiniciando sequências de identidade (RESTART IDENTITY CASCADE);
    • getTestPool() e closeTestPool(): Gerencia o pool de conexões do driver pg de forma singleton, encerrando conexões abertas no hook after() do test runner para impedir que o processo fique preso.
  • RF05 — Scripts Operacionais no package.json:
    • npm test: Executa todos os testes da suíte (unitários e de integração);
    • npm run test:unit: Executa apenas testes unitários em memória (ex.: auth.test.ts e audit.test.ts com repositório fake);
    • npm run test:integration: Executa testes de integração com banco de dados real (*.integration.test.ts);
    • npm run test:db:setup: Provisiona o banco de testes e roda migrações de forma avulsa pela linha de comando.
  • RF06 — Integração Contínua (CI): O job backend-ci em .github/workflows/ci-cd.yml deve subir um container de serviço postgres:18-alpine com healthcheck pg_isready e rodar a suíte completa de forma verde e estável.

Requisitos Não-Funcionais (RNF)

  • RNF01 — Velocidade e Performance: A suíte completa de testes de integração com banco real deve executar em menos de 10 segundos no ambiente local e no CI.
  • RNF02 — Idempotência e Confiabilidade: A execução repetida de npm test não deve acumular registros nem falhar por dependência de ordem entre testes.
  • RNF03 — Segurança e Sigilo (LGPD): Todos os usuários, senhas, e-mails, tokens e registros de auditoria utilizados em fixtures e testes devem ser estritamente fictícios e sintéticos.
  • RNF04 — Isolamento Estrito: Testes em execução nunca devem ler ou alterar o banco de desenvolvimento local (meubanco / aratu).

Cenários e Casos de Borda (Dado / Quando / Então)

Cenário 1: Banco de dados de teste inexistente na primeira execução

Dado que o desenvolvedor acabou de subir o container PostgreSQL local pelo Docker Compose e o banco aratu_test ainda não existe;
Quando a suíte de testes de integração ou o script npm run test:db:setup for acionado;
Então o helper de banco conecta ao banco de manutenção (postgres), executa CREATE DATABASE aratu_test, conecta ao novo banco e aplica todas as migrações SQL com sucesso.

Cenário 2: Migrações idempotentes no banco de teste já criado

Dado que o banco de dados aratu_test já possui tabelas e schemas criados de uma execução anterior;
Quando a suíte de testes é disparada novamente;
Então o migrator aplica as migrações transacionais sem emitir erros de colisão de schemas ou índices, deixando a base pronta para os testes.

Cenário 3: Limpeza de tabelas com integridade referencial ativa (Foreign Key)

Dado que a tabela audit.logs possui uma chave estrangeira referenciando auth.users(id) ON DELETE RESTRICT e ambas possuem registros inseridos pelo teste anterior;
Quando a função truncateTestDatabase() for acionada no hook beforeEach();
Então o comando TRUNCATE auth.users, audit.logs RESTART IDENTITY CASCADE esvazia ambas as tabelas sem violação de chave estrangeira e reinicia os contadores de identidade.

Cenário 4: Encerramento limpo do Pool do PostgreSQL

Dado que múltiplos testes abriram conexões no pool do PostgreSQL para executar consultas reais;
Quando a suíte de testes atinge o final da execução;
Então o hook after() invoca closeTestPool() liberando todos os clientes e clientes inativos, garantindo que o comando npm test finalize com código de saída 0 sem congelar o terminal.

4. Banco de Dados e Migrações (PostgreSQL 18)

A tarefa FROTA-161 não altera o schema nem cria novas tabelas no banco de dados de produção da FSPH/SVO. Seu propósito de banco é estruturar a gestão e a aplicação automatizada de migrações em um banco de testes isolado (aratu_test), garantindo que o PostgreSQL 18 reflita com 100% de paridade todas as tabelas de negócio já aprovadas.

Estrutura do Banco de Testes Isolado (aratu_test) e Suporte Dinâmico

O banco de testes é provisionado dinamicamente na mesma instância do PostgreSQL 18 (porta 5432 no Docker Compose ou no container de serviço do GitHub Actions). Para garantir desacoplamento total entre as branches main e develop, o migrador descobre e executa todas as migrações ativas presentes em backend/src/database/migrations/*.sql:

Ambiente / Branch Migrações Descobertas e Aplicadas Tabelas Criadas Dinamicamente Comportamento do Migrator
Estado atual na main 202610160001_create_users.sql public.users (PK id UUID, name, email, password_hash, role, is_active) e índice users_email_lower_unique Aplica a migração existente na main em transação atômica.
Após merge com a develop 202610160001_create_users.sql e 202610170001_create_audit.sql auth.users (PK id BIGINT) e audit.logs (PK id BIGINT, FK user_id) Reconhece e executa automaticamente as duas migrações em sequência ordenada sem necessidade de alterar nenhuma linha de código da suíte de testes.

Mecanismo de Execução e Transacionalidade (DDL Transacional)

O PostgreSQL 18 suporta DDL transacional nativo. O utilitário DatabaseMigrator encapsula a execução de cada arquivo .sql dentro de uma transação explícita com o PoolClient: 

// Padrão de execução dinâmica em backend/src/database/migrator.ts
await client.query('BEGIN;');
try {
  await client.query(sqlContent);
  await client.query('COMMIT;');
} catch (error) {
  await client.query('ROLLBACK;');
  throw error;
}

Estratégia de Limpeza Dinâmica entre Testes (Desacoplamento Total)

Para que a limpeza funcione tanto com as tabelas da main (public.users) quanto com as tabelas da develop (auth.users, audit.logs) e futuros módulos, a função truncateTestDatabase() consulta dinamicamente o information_schema.tables e executa o truncamento em cascata com reinício de sequências: 

// Limpeza dinâmica universal em backend/tests/helpers/db-test.ts
const { rows } = await pool.query<{ tname: string }>(`
  SELECT quote_ident(table_schema) || '.' || quote_ident(table_name) AS tname
    FROM information_schema.tables
   WHERE table_schema IN ('public', 'auth', 'audit', 'fleet', 'trip', 'svo')
     AND table_type = 'BASE TABLE';
`);

if (rows.length > 0) {
  const tableList = rows.map((r) => r.tname).join(', ');
  await pool.query(`TRUNCATE TABLE ${tableList} RESTART IDENTITY CASCADE;`);
}

Isso garante isolamento instantâneo (< 10ms) entre testes, sem acoplamento a nomes rígidos de tabelas e sem risco de violação de chave estrangeira.

Plano de Rollback

Por se tratar exclusivamente de infraestrutura de banco de teste:

  • Ambiente de Testes: Em caso de necessidade de reset estrutural completo, o comando SQL administrativo DROP DATABASE IF EXISTS aratu_test; destrói o banco de teste, permitindo que setupTestDatabase() o recrie limpo do zero.
  • Ambiente de Desenvolvimento/Produção: Nenhuma alteração física de DDL é executada nos bancos persistentes (meubanco / aratu), garantindo risco zero de regressão nos dados existentes.

5.2 Contratos TypeScript do Migrator (backend/src/database/migrator.ts)

import type { Pool, PoolClient } from 'pg';

export interface MigrationFile {
  filename: string;
  filepath: string;
  version: string;
  name: string;
}

export interface MigrationResult {
  version: string;
  name: string;
  durationMs: number;
  status: 'applied' | 'skipped';
}

/**
 * Utilitário responsável por descobrir, ordenar e executar arquivos SQL de migração
 * dentro de transações seguras no PostgreSQL 18.
 */
export class DatabaseMigrator {
  constructor(private readonly migrationsDirectory?: string) {}

  /** Carrega e ordena alfabeticamente os arquivos de migração .sql (ignorando .down.sql). */
  public async loadFiles(): Promise<MigrationFile[]>;

  /** Executa todas as migrações pendentes em transação atômica. */
  public async runMigrations(target: Pool | PoolClient, options?: { silent?: boolean }): Promise<MigrationResult[]>;
}

5.4 Detalhamento do Arquivo de Testes de Integração (backend/tests/database.integration.test.ts)

Embora esta tarefa trate de infraestrutura de backend e testes sem componentes visuais diretos, os princípios de acessibilidade da WCAG 2.2 Nível AA são resguardados através da clareza das mensagens de erro retornadas pela API e da garantia de que os testes asseguram que respostas com role="alert" e textos compreensíveis pelo usuário não sofram regressões.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

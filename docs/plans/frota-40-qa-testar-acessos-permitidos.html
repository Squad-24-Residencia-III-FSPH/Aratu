1. Contexto, Objetivo e Escopo

1.1 Contexto Operacional (FSPH / SVO)

O Sistema Aratu apoia os transportes sanitários de pacientes e insumos da Fundação de Saúde Parreiras Horta (FSPH) e os deslocamentos sensíveis de remoção e custódia cadavérica do Serviço de Verificação de Óbito (SVO). A segregação de funções entre os 6 perfis operacionais é uma salvaguarda jurídica e de privacidade indispensável. A segurança do sistema não pode depender do ocultamento cosmético de botões no frontend: toda rota protegida do Express 5 deve rejeitar chamadas de perfis não autorizados com HTTP 403 Forbidden.

1.2 Objetivo da Tarefa (FROTA-40)

Comprovar formalmente, através de testes automatizados e reprodutíveis no backend e checagem de roteamento no frontend, que o controle de acesso baseado em papéis (RBAC implementado nas tarefas FROTA-36, FROTA-37, FROTA-38 e FROTA-156) funciona sem falhas:

  1. Provisionar 6 usuários de teste no banco PostgreSQL 18 isolado (aratu_test), contemplando cada um dos 6 perfis RBAC canônicos com dados 100% fictícios (LGPD);
  2. Executar uma bateria de testes com no mínimo 12 casos de perfil (1 permitido [2xx] e 1 negado [403] para cada um dos 6 perfis) e casos gerais de integridade de autenticação (401 para ausência, expiração e adulteração de token);
  3. Integrar a suíte à rotina oficial npm test do backend sem alterar o banco de desenvolvimento;
  4. Comprovar que o frontend React 19 direciona cada perfil para seu destino exclusivo e bloqueia navegação para telas alheias.

1.3 Delimitação YAGNI (O que entra e o que NÃO entra)

  • Entra no escopo: Fixture de 6 usuários com perfis variados, suíte de testes de integração em backend/tests/rbac-access.integration.test.ts, testes de validação da matriz de 403/2xx, validação de tokens e conferência da suite de rotas do frontend.
  • Fora do escopo (YAGNI): Nenhuma alteração de DDL no PostgreSQL 18, nenhuma dependência externa pesada nova (o runner nativo tsx --test e node:assert/strict já suportam 100% do escopo) e nenhuma criação de tela nova no frontend.

2. Requisitos e Regras de Negócio (Casos de Borda)

2.1 Requisitos Funcionais (RF)

  • RF01 — Cobertura Completa dos 6 Perfis: A suíte deve instanciar usuários legítimos para ADMINISTRADOR, GESTOR, SOLICITANTE, MOTORISTA, ATENDENTE_SVO e EQUIPE_SVO.
  • RF02 — Testes de Acesso Permitido (2xx): Cada um dos 6 perfis deve obter sucesso (HTTP 200 OK) ao acessar endpoints autorizados para sua alçada (ex: ADMINISTRADOR em GET /profiles, e todos os 6 perfis em rotas autorizadas para seu papel na matriz RBAC e no encerramento de sessão POST /auth/logout).
  • RF03 — Testes de Acesso Negado (403 Forbidden): Cada perfil deve receber HTTP 403 ao chamar rota restrita a outro perfil, retornando obrigatoriamente a estrutura JSON: 
    { "erro": "Acesso negado: perfil de usuário não autorizado para esta operação." }
  • RF04 — Integridade e Ciclo de Vida do Token (401 Unauthorized):
    • Sem Token: Requisição a rota protegida sem cabeçalho Authorization → HTTP 401;
    • Token Malformado: Cabeçalho com valor diferente de Bearer <token> ou string corrompida → HTTP 401;
    • Token Expirado: Token assinado com exp no passado → HTTP 401;
    • Token Adulterado (Perfil Forjado): Token com payload alterado para perfil diferente da assinatura → HTTP 401;
    • Token com Perfil Inexistente: Token assinado com perfil fora do catálogo de roles → HTTP 401.
  • RF05 — Roteamento Frontend por Perfil: O roteador de tela do cliente deve manter a invariante de direcionar cada usuário autenticado exclusivamente para sua respectiva tela inicial (PROFILE_HOMES) e repelir sessões inválidas para /login.

2.2 Casos de Borda e Segurança

  • Tentativa de Escalação de Privilégio Horizontal: Um MOTORISTA não pode consultar perfis administrativos (GET /profiles → 403).
  • Tentativa de Escalação de Privilégio Vertical SVO: Um SOLICITANTE não pode acessar rotas da equipe do SVO (403).
  • Usuário Desativado com Token Ativo: Se um usuário for desativado no banco após emitir o token, nova tentativa de login deve ser repelida com 403 (LOGIN_INACTIVE).

4. Banco de Dados e Migrações (PostgreSQL 18)

Declaração de Impacto: Não se aplica alteração de DDL ou novas migrações a esta tarefa.

A tarefa valida o modelo existente já migrado na FROTA-156 (tabelas auth.roles, auth.permissions, auth.role_permissions e auth.users). O ciclo de testes interage exclusivamente com a base de dados de testes isolada aratu_test:

  • setupTestDatabase(): Cria o banco aratu_test caso não exista e executa o DatabaseMigrator aplicando as migrações SQL canônicas.
  • truncateTestDatabase(): Executa TRUNCATE ... RESTART IDENTITY CASCADE dinâmico via information_schema antes de cada ciclo de teste, mantendo a tabela de migrações (schema_migrations) e garantindo testes 100% isolados e determinísticos.
  • seedRolesAndPermissions(pool): Provisiona os 6 perfis RBAC oficiais e 18 permissões antes de cada suíte.

5.2 Detalhamento dos Componentes de Teste

  • backend/tests/fixtures/rbac-users.fixture.ts: Exporta uma fábrica centralizada para instanciar no banco aratu_test os 6 usuários de teste (um para cada perfil) com senhas criptografadas em bcrypt (custo padronizado) e dados 100% fictícios. Exporta também helper para geração de tokens JWT válidos para cada usuário.
  • backend/tests/rbac-access.integration.test.ts: Inicializa a aplicação Express via createApp({ pool, jwtConfig }), provisiona o banco e executa todas as requisições HTTP via cliente fetch em porta dinâmica efêmera (listen(0)), garantindo zero concorrência de portas e encerramento limpo de conexões no bloco finally.

6. Front-end — Telas, Componentes React 19 e Estados Visuais

Declaração de Impacto: Não se aplica criação ou alteração de componentes visuais React 19.

No frontend, o escopo de verificação da FROTA-40 é atendido e auditado por:

  • Validação da suite frontend/tests/routing.test.mjs: Garante que a função resolveRoute direciona cada perfil autenticado para sua rota raiz correspondente em PROFILE_HOMES e redireciona tentativas de acesso cruzado para a tela inicial do próprio perfil logado;
  • Proteção de Sessão: Sessão nula ou token expirado redireciona obrigatoriamente para /login;
  • Validação da integridade de aliases de perfis legíveis mapeados para os identificadores técnicos em frontend/src/auth/profiles.ts.

  • Rótulos e Erros (1.3.1, 3.3.1, 3.3.2): Todos os campos usam useId() conectando <label htmlFor> ao <input id>, aria-invalid e mensagem de erro com role="alert".

  • DATABASE_URL_TEST: String de conexão dedicada para o PostgreSQL 18 isolado (ex: postgresql://admin:admin123@127.0.0.1:5432/aratu_test).

9. Casos de Teste e Verificação

9.1 Bateria de Testes Automatizados da API (Backend — node:test + fetch)

A suíte backend/tests/rbac-access.integration.test.ts executará os seguintes 16 casos de teste automatizados integrados com PostgreSQL 18 real:

  1. IT-RBAC-01 (ADMINISTRADOR Permitido): Token de ADMINISTRADOR acessa GET /profiles → Status 200 e lista de perfis.
  2. IT-RBAC-02 (ADMINISTRADOR Negado): Token de ADMINISTRADOR acessa rota exclusiva de MOTORISTA → Status 403 e erro padronizado.
  3. IT-RBAC-03 (GESTOR Permitido): Token de GESTOR acessa rota exclusiva de gestor → Status 200.
  4. IT-RBAC-04 (GESTOR Negado): Token de GESTOR acessa GET /profiles → Status 403 e erro padronizado.
  5. IT-RBAC-05 (SOLICITANTE Permitido): Token de SOLICITANTE acessa rota exclusiva de solicitante → Status 200.
  6. IT-RBAC-06 (SOLICITANTE Negado): Token de SOLICITANTE acessa GET /profiles → Status 403 e erro padronizado.
  7. IT-RBAC-07 (MOTORISTA Permitido): Token de MOTORISTA acessa rota exclusiva de motorista → Status 200.
  8. IT-RBAC-08 (MOTORISTA Negado): Token de MOTORISTA acessa GET /profiles → Status 403 e erro padronizado.
  9. IT-RBAC-09 (ATENDENTE_SVO Permitido): Token de ATENDENTE_SVO acessa rota exclusiva de atendente SVO → Status 200.
  10. IT-RBAC-10 (ATENDENTE_SVO Negado): Token de ATENDENTE_SVO acessa GET /profiles → Status 403 e erro padronizado.
  11. IT-RBAC-11 (EQUIPE_SVO Permitido): Token de EQUIPE_SVO acessa rota exclusiva de equipe SVO → Status 200.
  12. IT-RBAC-12 (EQUIPE_SVO Negado): Token de EQUIPE_SVO acessa GET /profiles → Status 403 e erro padronizado.
  13. IT-RBAC-13 (Logout Permitido para Todos): Todos os 6 perfis autenticados realizam POST /auth/logout com sucesso → Status 200.
  14. IT-RBAC-14 (Sem Token / 401): Chamada a rota protegida sem header Authorization → Status 401.
  15. IT-RBAC-15 (Token Expirado / 401): Chamada a rota protegida com exp expirado → Status 401.
  16. IT-RBAC-16 (Token Adulterado / 401): Chamada com payload adulterado ou perfil forjado fora da assinatura → Status 401.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

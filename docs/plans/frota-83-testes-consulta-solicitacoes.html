1. Contexto, Objetivo e Escopo

Comprovar por testes automatizados que a API de consulta da US12 (FROTA-82) limita a visibilidade de solicitações por perfil e responde corretamente a filtros, paginação e detalhes de viagem. Esta subtarefa modifica apenas a suíte de testes e, quando necessário, fixtures fictícias de teste. Não altera API de produção, banco ou frontend.

Pré-condição: integrar FROTA-82 e executar a suíte sobre seus endpoints. FROTA-79 ainda não está na develop observada; os testes podem criar registros diretamente no banco de teste para manter isolamento da API de criação. Decisões de contrato confirmadas: status e campos em inglês, período por requested_date inclusivo, paginação no padrão de /users e dados agendados vindos de snapshots com fallback.

2. Requisitos e Regras de Negócio (Casos de Borda)

CasoDado / Quando / Então
Dois solicitantesDadas solicitações de A e B, quando A lista, então vê só as próprias; total e páginas não contam registros de B.
Detalhe alheioQuando A pede o ID de B, então recebe 404 com a mesma mensagem de um ID inexistente. B consulta o próprio ID e recebe 200.
GestãoQuando GESTOR ou ADMINISTRADOR lista, então vê A e B; quando consulta cada detalhe, recebe 200.
FiltrosDadas solicitações com status e datas diferentes, quando consulta status, from, to isolados ou combinados, então recebe somente as correspondentes, incluindo datas dos limites.
Entrada inválidaStatus desconhecido, data inexistente, período invertido, página não inteira, tamanho zero ou acima de 100 → 400, sem SQL executado com filtros inválidos.
AgendadaDada solicitação com viagem e snapshots históricos, quando pede detalhe, então recebe veículo, motorista e horários do agendamento. Sem snapshot, recebe fallback cadastral; sem viagem, trip: null.
AutorizaçãoSem token → 401; perfis fora de SOLICITANTE/GESTOR/ADMINISTRADOR → 403; conta inativa ou perfil alterado deve seguir a revalidação da sessão.

Os testes são de leitura: não esperam mutação de trip.requests, trip.trips, eventos ou auditoria causada pelos GETs.

4. Banco de Dados e Migrações (PostgreSQL 18)

Sem migração. O teste usa as tabelas existentes auth.users, fleet.services, fleet.vehicles, fleet.drivers, trip.requests e trip.trips. setupTestDatabase() aplica as migrações no banco de testes e truncateTestDatabase() isola cada caso; não tocar no banco de desenvolvimento ou produção. Todos os dados são fictícios, incluindo nomes, e-mails, placas e documentos.

Rollback: remover o arquivo de testes adicionado. Nenhuma alteração de schema ou dado persistente entra no produto.

5. Back-end — Contratos REST e Detalhamento por Arquivo (Express 5 / TS)

Esta subtarefa não define endpoints novos. Ela verifica o contrato de FROTA-82:

EndpointAsserções principais
GET /requests?status=&from=&to=&page=&pageSize=200 { requests, total, page, pageSize, totalPages }; status em inglês; ordem estável; filtros e contagem limitados ao perfil; 400/401/403.
GET /requests/:id200 com os campos da solicitação e trip nula ou detalhada; 404 para item alheio e inexistente; 400 para ID inválido; 401/403.

Não criar teste que dependa de detalhes privados do Repository quando a propriedade pode ser comprovada pela API e por consulta pontual ao banco de teste. O teste da dupla A/B deve provar a autorização por ID autenticado, sem parâmetro de usuário fornecido pelo cliente.

7. Acessibilidade (WCAG 2.2 Nível AA)

Verificar que erros 400 identificam o filtro inválido em texto compreensível para posterior apresentação acessível pela interface. A resposta 404 para solicitação alheia não pode expor existência ou proprietário. A API devolve status tipados em inglês para FROTA-84 mapear a rótulos textuais; a suíte desta tarefa não substitui testes de teclado, foco, contraste, zoom e anúncios dinâmicos da tela.

9. Casos de Teste e Verificação

  1. Preparação: before monta banco de teste migrado e servidor createApp em porta efêmera; beforeEach limpa tabelas, semeia papéis e usuários fictícios; after fecha servidor e pool. Seguir o padrão de requests-analysis.integration.test.ts.
  2. IT-REQUESTS-01: A e B têm dois pedidos cada. A lista e pagina; IDs e total contêm somente A. B também vê apenas B.
  3. IT-REQUESTS-02: A pede detalhe de B e ID inexistente; ambos 404 e mesmo corpo. A consulta o próprio, 200.
  4. IT-REQUESTS-03: GESTOR e ADMINISTRADOR recebem o conjunto A+B e consultam ambos os detalhes.
  5. IT-REQUESTS-04: status PENDING/APPROVED e datas antes/no/depois dos limites; testar status, from, to e combinação, inclusive limite inclusivo.
  6. IT-REQUESTS-05: status desconhecido, data malformada ou inexistente, from > to, page=0, pageSize=101 e parâmetros repetidos retornam 400.
  7. IT-REQUESTS-06: solicitação agendada com viagem e snapshots diferentes dos cadastros atuais prova uso histórico de placa/nome; outra viagem sem snapshots prova fallback; pedido sem viagem retorna trip: null.
  8. IT-REQUESTS-07: sem token 401, perfis excluídos 403, conta inativa 401 e troca de perfil respeitada quando houver middleware de revalidação.
  9. IT-REQUESTS-08: verificar ordenação e metadados em duas páginas, página além do fim vazia e ausência de mutações em trip.request_events/audit.logs após GETs.
  10. Execução: cd backend && npm test deve passar integralmente; npx tsc --noEmit sem erros. Inspecionar respostas e SQL contra banco de teste, sem usar dados reais.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMINISTRADOR, GESTOR, SOLICITANTE, MOTORISTA, ATENDENTE_SVO, EQUIPE_SVO).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

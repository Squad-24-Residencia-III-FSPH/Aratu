1. Contexto, Objetivo e Escopo

O Gestor de Frota consulta viagens finalizadas da FSPH, verifica os dados de execução disponíveis e confirma a conclusão quando as quilometragens inicial e final estiverem presentes.

  • Problema atual: A API FROTA-106 permite listar e confirmar viagens, mas o frontend ainda não oferece a tela operacional de conferência.
  • Resultado esperado: Página integrada à navegação autenticada para filtrar viagens, inspecionar dados suportados e confirmar uma viagem com confirmação explícita.

1.1 Delimitação de Escopo (YAGNI)

  • Entra: página React responsiva; acesso GESTOR; período via API e veículo/motorista filtrados localmente; solicitação (identificador, origem e destino), status, veículo, motorista, horários planejados/realizados, hodômetros e distância; confirmação via ConfirmDialog; estados e mensagens de erro.
  • Fora: backend/banco; tipo de serviço e fotos do hodômetro, ausentes no contrato; solicitar correção/reabrir viagem; paginação e filtros remotos por veículo/motorista.
  • Contrato: não inventar dados nem endpoints. Distância é endKm - startKm quando ambos existem; sem qualquer hodômetro, não confirmar.

2. Requisitos e Regras de Negócio (Casos de Borda)

  • Dado Gestor autenticado, quando abrir a tela, então carregar GET /trips?status=FINISHED.
  • Dado período informado, quando aplicar os filtros, então enviar from/to como YYYY-MM-DD; a API considera to inclusivo em America/Maceio.
  • Dado viagens carregadas, quando selecionar veículo ou motorista, então filtrar localmente por placa/nome da resposta; limpar filtros restaura a lista recebida.
  • Dado viagem FINISHED com startKm/endKm, quando confirmar no diálogo, então enviar POST /trips/:id/confirm e atualizar a lista após sucesso.
  • Dado hodômetro ausente, quando abrir detalhes, então desabilitar confirmação e explicar a exigência.
  • Dado resposta de erro { erro }, quando houver falha, então apresentar a mensagem da API quando aplicável; 409 orienta atualizar a lista.
  • Dado perfil diferente de GESTOR, quando acessar a rota, então redirecionar à página inicial do perfil.
  • Qualidade: TypeScript estrito, layout responsivo, operação por teclado, foco visível e feedback anunciado.

5. Back-end — Contratos REST e Detalhamento por Arquivo (Express 5 / TS)

Nenhuma mudança backend. Contrato conferido em backend/src/routes/trips.routes.ts, controller, service, repository e types/trip.types.ts de origin/develop.

Método e rotaAcessoContrato consumido
GET /trips?status=FINISHED&from=&to=GESTOR200 array de { id, requestId, status, scheduledStart, scheduledEnd, startedAt, finishedAt, startKm, endKm, vehicleLicensePlate, driverName, origin, destination, confirmedBy, confirmedAt }; 400 para filtros inválidos. Datas YYYY-MM-DD; to inclusivo.
POST /trips/:id/confirmGESTORBody opcional { reason? }, envio sem body permitido; 200 { id, status: "CONFIRMED", confirmedBy, confirmedAt, revision }; 400/404/409/422 com mensagem em erro.

A API valida a transição FINISHED → CONFIRMED e exige startKm e endKm. A UI não altera esse comportamento nem o backend.

6. Front-end — Telas, Componentes React 19 e Estados Visuais

A tela usará PageHeader, FilterBar, FormField/FormSelect, DataTable, StateFeedback, StatusChip e ConfirmDialog. Detalhes são apresentados em diálogo acessível acionado por “Ver detalhes”.

EstadoComportamento
IdealLista/detalhes da viagem; confirmar só com ambos os hodômetros.
CarregandoStateFeedback loading e aria-busy na lista.
VazioMensagem para lista vazia ou filtros sem resultados e opção de limpar filtros.
ErroStateFeedback error com retry e mensagem erro da API quando aplicável.
ParcialConfirmação concluída, mas atualização da lista falhou: preservar feedback de sucesso e oferecer atualização.

Tipo de serviço e fotos não serão renderizados, pois não existem no contrato. Veículo e motorista são filtros locais por placa/nome recebidos, sem catálogos ou IDs adicionais.

  • Tamanho do Alvo (2.5.8): Botões e controles interativos possuem área mínima de 44×44px em telas operacionais.
  • Contraste e Uso de Cor (1.4.1, 1.4.3, 1.4.11): Contraste de texto >= 4.5:1 e status acompanhado de rótulo textual além da cor.
  • Mensagens de Status (4.1.3): Feedbacks dinâmicos anunciados via role="status" ou aria-live="polite".
  • Diálogo nomeia a viagem, fecha por Esc e devolve foco ao acionador.
  • Conteúdo reflow sem rolagem horizontal da página a 320px e zoom 200%.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

1. Contexto, Objetivo e Escopo

No domínio operacional da Fundação de Saúde Parreiras Horta (FSPH) e do Serviço de Verificação de Óbito (SVO), a rastreabilidade das operações executadas no Sistema Aratu é um requisito crítico de governança, conformidade com a LGPD e auditoria administrativa. Toda ação relevante — desde autenticação e encerramento de sessão até futuras operações sobre veículos, motoristas, solicitações de viagem e atendimentos do SVO — precisa registrar de forma padronizada e imutável quem realizou a operação, o que foi feito, em qual entidade/registro ocorreu e o instante exato.

Esta tarefa (FROTA-139, que incorpora o escopo da antiga FROTA-140) entrega a infraestrutura central de auditoria no backend (PostgreSQL 18 + Node.js/Express 5/TypeScript) e estrutura as tabelas de usuários (auth.users) e auditoria (audit.logs) sob schemas nativos de domínio do PostgreSQL 18 no padrão plural (<schema>.<plural_entity>).

Decisões Confirmadas pela Regra da Dúvida

  1. Estrutura de Schemas Nativos (auth.users e audit.logs): A migration inicial 202610160001_create_users.sql cria o schema auth e a tabela auth.users com id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, e a nova migration 202610170001_create_audit.sql cria o schema audit e a tabela audit.logs referenciando user_id BIGINT REFERENCES auth.users(id) ON DELETE RESTRICT.
  2. Estrutura Completa da Tabela audit.logs: Serão contempladas as colunas canônicas do manual (id, user_id, table_name, record_id, operation, before, after, actor_snapshot, reason, registered_at).
  3. Nomenclatura e Transacionalidade do Utilitário: Respeitando a regra C4 do aratu-check.mjs e o Clean Code em inglês, o acesso SQL fica isolado em AuditRepository e a regra em AuditService (expondo o método e helper recordAudit em inglês), aceitando um PoolClient opcional para rodar na mesma transação (BEGIN ... 2. Requisitos e Regras de Negócio (Casos de Borda)

Cenários Operacionais (Dado / Quando / Então)

Cenário 1 — Gravação de auditoria por operação de negócio autenticada

  • Dado que um serviço de domínio executa uma operação relevante em nome de um usuário autenticado (ex.: login bem-sucedido, logout ou futura alteração de frota/viagem);
  • Quando o serviço invoca auditService.recordAudit(input, client) informando userId, table, recordId, operation e metadados opcionais (before, after, actorSnapshot, reason);
  • Então um novo registro imutável é inserido em audit.logs com carimbo temporal clock_timestamp() e retornado com seus campos mapeados em camelCase.

Cenário 2 — Atomicidade transacional via PoolClient

  • Dado que um módulo executa uma operação crítica dentro de uma transação explícita (BEGIN ... COMMIT) usando um PoolClient;
  • Quando recordAudit(input, client) é chamado passando o mesmo client transacional e ocorre uma falha na gravação da auditoria ou em etapa posterior da transação;
  • Então o ROLLBACK da transação desfaz tanto a operação de negócio quanto o registro de auditoria, impedindo estados órfãos ou alterações sem rastro.

Cenário 3 — Rastreio de operações de autenticação (/auth/login e /auth/logout)

  • Dado que um usuário envia credenciais para POST /auth/login ou encerra a sessão em POST /auth/logout;
  • Quando:
    1. As credenciais são válidas e a conta está ativa → grava operation = 'LOGIN_SUCCESS', table_name = 'auth.users', user_id = Number(user.id), record_id = user.id e actor_snapshot com { id, email, role };
    2. A senha é incorreta para usuário existente → grava operation = 'LOGIN_FAILURE', table_name = 'auth.users', user_id = Number(user.id), record_id = user.id, reason = 'Invalid password';
    3. O e-mail informado não corresponde a nenhum usuário → grava operation = 'LOGIN_FAILURE', table_name = 'auth.users', user_id = null, record_id = null, actor_snapshot = { email: normalizedEmail }, reason = 'User not found';
    4. A conta está inativa (active = false) → grava operation = 'LOGIN_INACTIVE', table_name = 'auth.users', user_id = Number(user.id), record_id = user.id, reason = 'Inactive user account';
    5. O usuário autenticado chama POST /auth/logout → grava operation = 'LOGOUT', table_name = 'auth.users', user_id = Number(req.usuario.id) (quando numérico válido), record_id = req.usuario.id e actor_snapshot = { id: req.usuario.id, role: req.usuario.perfil }.
  • Então todas as ocorrências ficam rastreadas em audit.logs sem nunca registrar a senha em texto puro ou o hash bcrypt nos snapshots (proteção LGPD e segurança).

Cenário 4 — Validação de entrada obrigatória no AuditService

  • Dado que um chamador invoca recordAudit() com table vazio ou operation vazia;
  • Quando o AuditService valida os parâmetros antes de chamar o AuditRepository;
  • Então lança erro descritivo em português informando que a tabela/entidade e a operação auditada são obrigatórias, sem enviar query inválida ao PostgreSQL.

4. Banco de Dados e Migrações (PostgreSQL 18)

4.1 Reescrita da Migration de Usuários (202610160001_create_users.sql)

BEGIN;

CREATE SCHEMA IF NOT EXISTS auth;

DROP TABLE IF EXISTS usr_user CASCADE;
DROP TABLE IF EXISTS auth.users CASCADE;
DROP TABLE IF EXISTS auth.user CASCADE;

CREATE TABLE auth.users (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL CHECK (btrim(name) <> ''),
  email TEXT NOT NULL CHECK (btrim(email) <> ''),
  password_hash TEXT NOT NULL CHECK (btrim(password_hash) <> ''),
  role TEXT NOT NULL CHECK (role IN (
    'ADMINISTRADOR',
    'GESTOR',
    'SOLICITANTE',
    'MOTORISTA',
    'ATENDENTE_SVO',
    'EQUIPE_SVO'
  )),
  active BOOLEAN NOT NULL DEFAULT true,
  revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE UNIQUE INDEX auth_users_email_lower_unique ON auth.users (lower(email));

COMMIT;

Plano de Rollback (202610160001_create_users.down.sql)

BEGIN;

DROP INDEX IF EXISTS auth_users_email_lower_unique;
DROP TABLE IF EXISTS auth.users;

COMMIT;

4.2 Nova Migration da Tabela de Auditoria (202610170001_create_audit.sql)

Cada linha de audit.logs registra que o ator user_id (ou tentativa anônima documentada em actor_snapshot) executou a operação operation sobre o registro record_id da tabela/entidade table_name no instante registered_at. 

BEGIN;

CREATE SCHEMA IF NOT EXISTS audit;

DROP TABLE IF EXISTS aud_audit CASCADE;
DROP TABLE IF EXISTS audit.logs CASCADE;
DROP TABLE IF EXISTS audit.log CASCADE;

CREATE TABLE audit.logs (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id BIGINT REFERENCES auth.users (id) ON DELETE RESTRICT,
  table_name TEXT NOT NULL CHECK (btrim(table_name) <> ''),
  record_id TEXT CHECK (record_id IS NULL OR btrim(record_id) <> ''),
  operation TEXT NOT NULL CHECK (btrim(operation) <> ''),
  before JSONB,
  after JSONB,
  actor_snapshot JSONB,
  reason TEXT CHECK (reason IS NULL OR btrim(reason) <> ''),
  registered_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE INDEX audit_logs_by_table ON audit.logs (table_name, record_id);
CREATE INDEX audit_logs_by_user ON audit.logs (user_id);
CREATE INDEX audit_logs_by_registered_at ON audit.logs (registered_at DESC, id DESC);

COMMIT;

Plano de Rollback (202610170001_create_audit.down.sql)

BEGIN;

DROP INDEX IF EXISTS audit_logs_by_registered_at;
DROP INDEX IF EXISTS audit_logs_by_user;
DROP INDEX IF EXISTS audit_logs_by_table;
DROP TABLE IF EXISTS audit.logs;

COMMIT;

5. Back-end — Contratos REST e Detalhamento por Arquivo (Express 5 / TS)

5.1 Impacto nos Endpoints REST Existentes

Conforme decisão confirmada (YAGNI), esta tarefa não cria novos endpoints HTTP, mas integra a gravação automática de auditoria nos endpoints de autenticação existentes mantendo 100% do contrato JSON de entrada e saída com o frontend:

Método e Rota Autenticação Operações Auditadas em audit.logs Respostas HTTP (Inalteradas)
POST /auth/login Pública
  • LOGIN_SUCCESS (200): grava user_id, record_id = user.id, actor_snapshot = { id, email, role }.
  • LOGIN_FAILURE (401): grava tentativa com senha inválida ou e-mail inexistente (sem jamais gravar a senha).
  • LOGIN_INACTIVE (403): grava tentativa bloqueada de conta inativa.
 200 OK, 400 Bad Request, 401 Unauthorized, 403 Forbidden
POST /auth/logout Bearer JWT (createAuthMiddleware)
  • LOGOUT (200): grava encerramento de sessão com user_id, record_id = req.usuario.id e actor_snapshot = { id, role }.
 200 OK, 401 Unauthorized

5.2 Contratos e Tipagens (backend/src/types/audit.types.ts)

import type { PoolClient } from 'pg'

export type AuditOperation =
  | 'CREATE'
  | 'UPDATE'
  | 'DELETE'
  | 'STATUS_CHANGE'
  | 'LOGIN_SUCCESS'
  | 'LOGIN_FAILURE'
  | 'LOGIN_INACTIVE'
  | 'LOGOUT'
  | (string & {})

export interface AuditActorSnapshot {
  id?: string
  email?: string
  role?: string
  [key: string]: unknown
}

export interface CreateAuditInput {
  userId?: string | number | null
  table: string
  recordId?: string | number | null
  operation: AuditOperation
  before?: Record<string, unknown> | null
  after?: Record<string, unknown> | null
  actorSnapshot?: AuditActorSnapshot | null
  reason?: string | null
}

export interface NormalizedCreateAuditInput {
  userId: string | null
  table: string
  recordId: string | null
  operation: string
  before: Record<string, unknown> | null
  after: Record<string, unknown> | null
  actorSnapshot: AuditActorSnapshot | null
  reason: string | null
}

export interface AuditEntry {
  id: string
  userId: string | null
  table: string
  recordId: string | null
  operation: string
  before: Record<string, unknown> | null
  after: Record<string, unknown> | null
  actorSnapshot: AuditActorSnapshot | null
  reason: string | null
  registeredAt: Date
}

export interface AuditRepositoryContract {
  create(input: NormalizedCreateAuditInput, client?: PoolClient): Promise<AuditEntry>
}

export interface AuditLogger {
  recordAudit(input: CreateAuditInput, client?: PoolClient): Promise<AuditEntry>
}

5.3 Camada de Repositório (backend/src/repositories/audit.repository.ts)

  • Implementa AuditRepositoryContract recebendo Pool no construtor e aceitando client?: PoolClient no método create para participar de transações atômicas.
  • Utiliza placeholders posicionais ($1..$8), converte objetos JSON com serialização segura para $5::jsonb, $6::jsonb, $7::jsonb e projeta explicitamente as colunas com id::text AS id e aliases em camelCase (proibido SELECT * ou RETURNING *).

5.4 Camada de Serviço e Helper Único (backend/src/services/audit.service.ts)

  • Implementa AuditService sem nenhuma dependência de Express ou HTTP.
  • Valida que table e operation são strings não vazias após trim(); normaliza userId numérico positivo (ou null quando ausente/não numérico em mocks) e recordId como string limpa.
  • Exporta também a fábrica utilitária createRecordAudit(repository) para casos em que módulos queiram injetar diretamente a função recordAudit(input, client).

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 com schemas nativos de domínio (auth, audit, fleet, trip, svo).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

2. Requisitos e Regras de Negócio (Casos de Borda)

2.1 Requisitos Funcionais e Cenários (Dado / Quando / Então)

  • RF1 — [Fluxo Principal]: Dado que o usuário com perfil <ROLE> informa <dados>, Quando aciona <ação>, Então o sistema valida <regra> e registra <estado esperado>.
  • RF2 — [Concorrência / Conflito de Agenda]: Dado que duas requisições simultâneas tentam alocar a mesma viatura ou motorista para horários sobrepostos, Quando a transação é executada com SELECT ... FOR UPDATE, Então a primeira conclui a alocação e a segunda recebe erro 409 Conflict com mensagem orientadora.
  • RF3 — [Transição de Estado]: As únicas transições permitidas para o estado da viagem são: PLANNED → IN_PROGRESS → COMPLETED (ou CANCELED). Qualquer transição fora deste grafo retorna 422 Unprocessable Entity.

2.2 Requisitos Não-Funcionais

  • RNF1 — Atomicidade e Idempotência: Operações compostas no banco utilizam transação explícita (BEGIN ... COMMIT / ROLLBACK) com liberação garantida do cliente no bloco finally.
  • RNF2 — Acessibilidade: Conformidade integral com a WCAG 2.2 Nível AA (foco por teclado, useId(), alvos mínimos de 44×44px no fluxo móvel e anúncios via aria-live).
  • RNF3 — Proteção de Dados (LGPD e Sigilo SVO): Dados sensíveis restritos aos perfis autorizados; zero dados pessoais reais em testes, seeds ou logs.

4. Banco de Dados e Migrações (PostgreSQL 18)

4.1 Novas Tabelas / Alterações de Schema (DDL Transacional — Schemas Nativos)

-- Migration: backend/src/database/migrations/NNN_<description>.sql
BEGIN;

CREATE SCHEMA IF NOT EXISTS trip;

CREATE TABLE trip.trips (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    vehicle_id bigint NOT NULL REFERENCES fleet.vehicles ON DELETE RESTRICT,
    driver_id bigint NOT NULL REFERENCES fleet.drivers ON DELETE RESTRICT,
    planned_departure timestamptz NOT NULL,
    planned_end timestamptz NULL,
    state text NOT NULL DEFAULT 'PLANNED' CHECK (state IN ('PLANNED', 'IN_PROGRESS', 'COMPLETED', 'CANCELED')),
    revision integer NOT NULL DEFAULT 1 CHECK (revision > 0),
    created_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    CHECK (planned_end IS NULL OR planned_end > planned_departure)
);

-- Índices no padrão <schema>_<entity>_<purpose> (sem idx_ ou uq_)
CREATE UNIQUE INDEX trip_trips_vehicle_in_progress ON trip.trips (vehicle_id) WHERE state = 'IN_PROGRESS';
CREATE UNIQUE INDEX trip_trips_driver_in_progress ON trip.trips (driver_id) WHERE state = 'IN_PROGRESS';

COMMIT;
Convenções obrigatórias do PostgreSQL 18 no Aratu:
  • Schemas nativos por domínio (auth, audit, fleet, trip, svo); tabelas no plural sem prefixo abreviado (<schema>.<plural_entity>); PK id BIGINT GENERATED ALWAYS AS IDENTITY; colunas substantivas limpas (name, email, state); FKs limpas <entity>_id (ou <entity>_id_<role>).
  • Índices no padrão <schema>_<entity>_<purpose> (sem idx_/uq_); triggers e funções sem trg_/fn_; views com vw_.
  • Medidas numéricas ainda não informadas (ex: odometer quando não aplicável) permanecem NULL, nunca zero.
  • Compatibilidade de dados: se alterar tabela que já contém registros, explicitar como as linhas existentes serão migradas.

4.2 Plano de Rollback (Obrigatório quando houver Migration)

BEGIN;
DROP INDEX IF EXISTS trip_trips_driver_in_progress;
DROP INDEX IF EXISTS trip_trips_vehicle_in_progress;
DROP TABLE IF EXISTS trip.trips;
COMMIT;

9. Casos de Teste e Verificação

Todos os cenários utilizam exclusivamente dados fictícios e sintéticos (conformidade estrita com a LGPD e sigilo do SVO).

9.1 Testes Automatizados (Unitários em Service e Integração em Repository)

  • CT-U01 (Caminho Feliz): Dados válidos no Service → persiste registro com estado inicial correto.
  • CT-U02 (Regra de Domínio): Tentativa de operação com veículo inativo, capacidade excedida ou hodômetro inválido → lança erro de domínio esperado.
  • CT-I01 (Concorrência e Transação PostgreSQL 18): Duas chamadas simultâneas de alocação sobre a mesma viatura → o lock SELECT ... FOR UPDATE garante apenas uma alocação e faz ROLLBACK limpo na outra.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 com schemas nativos de domínio em inglês.
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

2. Requisitos e Regras de Negócio (Casos de Borda)

Plano de execução em ordem

  1. P0 — Recuperar governança e simplificar Gitflow. Remover promoção via staging. Após atualizar referências remotas, confirmar ancestralidade e PRs abertos; retirar dependências dos workflows e só então excluir staging. Em 17/11/2026, staging não tem commits exclusivos frente a develop (0/213). O usuário confirmou ser administrador. Confirmar um administrador e um substituto com acesso ao repositório e às contas Cloudflare, Render e Neon. Registrar projetos, URLs, responsáveis e recuperação de acesso, sem senhas na documentação. Inventariar o que ainda existe no GitHub: Environment production, nomes de secrets/vars, regras de branches e integrações. Não excluir recursos antigos nem presumir perda ou inexistência de dados.
  2. P1 — Tornar o CI verificável. Separar validação, promoção e publicação; adicionar gate final que falhe se qualquer check obrigatório falhar, for cancelado ou pulado. Registrar contagem de testes executados/falhos/pulados e salvar relatórios mesmo com falha. Manter banco descartável PostgreSQL 18 no runner. Atualizar actions que emitem avisos de Node 20 para versões suportadas por Node 24 e fixar versões verificadas; escolher uma imagem Ubuntu explícita validada para evitar migração silenciosa de ubuntu-latest.
  3. P2 — Preparar pacote e banco. Copiar SQL para dist e disponibilizar comandos Node compilados. Validar imagem real com PostgreSQL limpo, migrations e autenticação sintética. Criar Neon PG18 novo e aplicar migrations do SHA aprovado, com URL direta e TLS. Provisionar contas fictícias por perfil sem reset automático.
  4. P3 — Publicar API no Render Free. Vincular repositório/branch main, runtime Node 24 via Dockerfile.prod e porta PORT. Desativar autodeploy independente: Actions será a autoridade de publicação. Acionar a API de deploy com commitId do SHA aprovado e acompanhar até ficar live; não considerar HTTP 201/202 como deploy concluído.
  5. P4 — Publicar frontend no Pages Free. Compilar com VITE_API_BASE_URL apontando para a origem HTTPS da API, sem sufixo /api; enviar dist pelo Actions após API saudável. Configurar navegação SPA, validar recarga em rota autenticada e CORS.
  6. P5 — Homologar e entregar acesso. Testar login e operações permitidas/proibidas dos seis perfis, retomada após inatividade, persistência após redeploy e rollback. Entregar URL e credenciais por canal privado autorizado, com roteiro de teste e dois responsáveis documentados.

Critérios de aceite

  • Dado um PR para develop/main, quando CI executa, então as suítes obrigatórias rodam; nenhum deploy é iniciado e o PR mostra somente checks de validação.
  • Dado lint ou teste falhando, então o gate final falha, o log identifica a etapa raiz e o merge fica bloqueado pelas regras configuradas.
  • Dado um push aprovado em main, então migrations e serviços publicados correspondem ao mesmo SHA. Se migrations falharem, a API nova e o frontend novo não são publicados.
  • Dado um serviço adormecido, quando o usuário entra ou retoma a sessão, então recebe feedback acessível de preparação e uma espera limitada; senhas inválidas continuam retornando erro de credenciais.
  • Dado cada perfil, então há uma conta independente e as permissões reais continuam sendo verificadas pelo backend; acesso aos seis perfis não significa permissões irrestritas numa única conta.
  • Dado um redeploy, então os registros persistem no Neon. Nenhum job de CI ou fixture aponta para a base de homologação.

4. Banco de Dados e Migrações (PostgreSQL 18)

Não há novo schema de negócio proposto. Aplicar as migrations existentes no commit aprovado numa base Neon PostgreSQL 18 nova (21 na develop atualizada em 17/11/2026); manter auth, audit, fleet, trip e svo. O passado do banco antigo não é reconstruído a partir de seeds.

  1. Na conta controlada pela equipe, criar projeto Neon Free de homologação; preferir região próxima da API entre as opções disponíveis. Usar conexão TLS gerada pelo Neon e banco exclusivo.
  2. Preparar dist/database/migrations com todos os SQL e validar que a quantidade corresponde à origem. Hoje loadFiles() retorna lista vazia quando não encontra a pasta; para a execução de produção, ausência de migrations deve ser erro explícito.
  3. No job protegido, executar node dist/database/scripts/migrate.js, com DATABASE_URL apontando à conexão direta de migração. Serializar releases do mesmo ambiente; não executar um migrador por réplica nem no arranque a cada cold start.
  4. Usar o DatabaseMigrator existente: transação por migration e controle em schema_migrations. Aplicações novas exigem migrations compatíveis com a versão anterior, pois a API antiga ainda pode estar ativa durante a atualização.
  5. Provisionar matriz RBAC e contas fictícias por comando manual idempotente, reaproveitando funções existentes. O seed atual inclui frota/equipe SVO além do administrador; não assumir que ele já cria os seis logins de homologação.

Para uma API única, começar com conexão direta TLS e pool pg limitado; medir conexões e latência antes de adotar pooling externo. Não usar os helpers destrutivos de testes no Neon. O CI permanece no PostgreSQL descartável do GitHub, com DATABASE_URL_TEST explícita e distinta da base compartilhada.

Backup e rollback

Antes de migrations futuras, gerar exportação lógica e conferir restauração numa base de verificação autorizada. A janela gratuita de restore do Neon é curta; não substitui um procedimento de backup testado. Guardar exportação fora do repositório e de artefatos públicos.

Se a API nova falhar, não publicar frontend novo; restaurar o último deploy estável no Render e a publicação correspondente no Pages. Reverter aplicação não reverte schema. Não executar .down.sql automaticamente nem apagar registros; avaliar reversão conforme dados gravados. Banco antigo só será migrado após obter acesso, inventário e decisão explícita sobre o que preservar.

6. Front-end — Telas, Componentes React 19 e Estados Visuais

O frontend já suporta VITE_API_BASE_URL em AuthProvider.tsx. Na build de homologação, apontar para https://<servico>.onrender.com, sem /api: as rotas Express são /auth, /vehicles etc. O prefixo /api é removido pelo Nginx atual e pelo proxy Vite; esse proxy de desenvolvimento não existe no Pages.

Gerar frontend/dist com Node 24, lockfile e URL HTTPS definidos no build. VITE_* é conteúdo público; nunca colocar secrets nessas variáveis. Publicar por Direct Upload em projeto Pages com branch de publicação main e fallback SPA verificado em rota profunda. O npm da raiz não substitui os dois projetos independentes.

Retomada após suspensão

Hoje loginService e api/client usam timeout de 15 segundos. Acrescentar preparação de disponibilidade com GET /health/ready antes do POST de login e quando a sessão for retomada após inatividade. A espera terá orçamento total de até 120 segundos, tentativa cancelável e feedback; não classificar cold start como credencial inválida. Limitar retries a sondagens GET: não repetir automaticamente POST/PATCH de operações de negócio.

7. Acessibilidade (WCAG 2.2 Nível AA)

  • Texto de preparação anunciado por role="status"/aria-live="polite"; erro por role="alert", sem anúncios repetidos a cada sondagem.
  • Botões “Cancelar espera” e “Tentar novamente” operáveis por teclado, foco visível e área de toque de 44×44 px.
  • Não apagar preenchimento durante retomada nem bloquear colar senha. Gerenciar foco após cancelamento ou erro sem deslocamento automático repetido.

  • O relatório usa títulos semânticos, idioma pt-BR e tabelas com cabeçalhos; acessibilidade não depende apenas de cores.

Gitflow e gates

Adotar o fluxo solicitado feature/fix → develop → main. Promover por PR manual e remover staging após retirar dependências e verificar PRs abertos. Usar uma única homologação gratuita publicada pela main, sem outro servidor de testes. Atualizar referências e reconciliar divergências por PR; não resetar/forçar branches.

ci-required usa condição always() e exige success de frontend-ci, backend-ci e docker-ci; skipped e cancelled não aprovam. Preservar checks obrigatórios atuais durante a migração e exigir o gate em develop e main. Publicação chama a mesma validação por workflow_call, dispensando eventos privilegiados de PR ou dependência circular entre plataformas.

Serializar o CD por ambiente com cancel-in-progress=false, incluindo migrations e publicação dos dois serviços. Cancelar execuções obsoletas de PR é aceitável; não cancelar deploy durante migração. Conferir head da main antes de iniciar uma release enfileirada e registrar SHA, IDs de deploy e URLs no resumo.

Consultar o deploy Render por ID até live/failed/cancelled; confirmar commitId e readiness antes de publicar Pages. Desativar autodeploy separado nas plataformas. Render aceita commitId específico; Cloudflare recebe o dist do mesmo SHA. HTTP de aceitação do pedido não basta.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: preservar os perfis reais ADMINISTRADOR, GESTOR, SOLICITANTE, MOTORISTA, ATENDENTE_SVO e EQUIPE_SVO, conforme o código atual.
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

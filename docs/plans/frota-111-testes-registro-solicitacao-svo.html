4. Banco de Dados e Migrações (PostgreSQL 18)

Nenhuma migration de produção. Aplicar a migration existente pelo DatabaseMigrator via setupTestDatabase e usar apenas a conexão de teste. Antes de qualquer limpeza, verificar explicitamente que a URL aponta para banco de testes e não para a base operacional, sem imprimir credenciais.

  • before: aplicar migrations, obter pool, iniciar createApp em porta efêmera e esperar listening.
  • beforeEach: truncateTestDatabase no banco isolado, seedRolesAndPermissions e seedRbacTestUsers; não truncar entre requisições de um caso concorrente.
  • Testes por HTTP usam conexões próprias: um ROLLBACK externo ao teste não desfaz commits da aplicação. Por isso a limpeza HTTP segue o helper do projeto.
  • Verificações diretas de constraints/imutabilidade no Repository usam PoolClient dedicado com BEGIN e ROLLBACK no finally. A transação que recebeu erro de trigger precisa de rollback antes de nova consulta.
  • after: fechar servidor e pool; remover somente instrumentação de teste, sem modificar triggers de produção.

Rollback: a suíte deve comprovar rollback da operação sob falha e não requer .down.sql. Ao reverter a entrega de QA, remover apenas código de testes/documentação correspondente; preservar todos os dados de negócio. Nunca executar TRUNCATE, DELETE ou .down.sql em produção.

Asserções seguem exatamente as projeções e DTOs da FROTA-112; respostas de erro usam { erro: string } não vazia e orientadora. Testar BIGINT sem conversão para number, datas ISO com fuso, query malformada e propriedades controladas pelo servidor.

Fixtures de legado: respeitar NOT NULL e CHECK da migration atual. Não desabilitar constraints nem inserir campos obrigatórios vazios/nulos para simular legado impossível. A defesa do service contra dados incompletos retornados por um repository substituto pertence aos testes unitários da FROTA-112; SVO-19 usa somente combinações persistíveis na base real.

Instrumentação de falhas

  • Falha de auditoria: createApp já aceita audits (AuditRepositoryContract); injetar repositório que falha de maneira determinística durante CREATE ou STATUS_CHANGE e comparar a base antes/depois. Essa variante usa o mesmo Pool e portas efêmeras isoladas.
  • Falha de evento: em banco exclusivamente de teste, instalar trigger temporário que lança exceção para uma sentinela sintética controlada; removê-lo em finally mesmo se houver falha de asserção. Não substituir o trigger append-only existente.
  • Concorrência: disparar dois fetch POST confirm sobre o mesmo id com Promise.all; verificar respostas [200,409], revision final e contagens exatas de eventos/auditoria.
  • Sigilo: usar sentinelas diferentes em nome, telefone, local, descrição, notes e evidenceDescription; buscar recursivamente em before/after de audit.logs e capturar diagnóstico da aplicação. Dados devem existir no histórico restrito quando aplicável, mas estar ausentes dos logs.
  • Erro SQL: forçar no banco isolado erro cujo detalhe contenha a sentinela; capturar a saída real do processo/console usado pelo handler SVO, sem deixar mocks globais ativos entre testes. Verificar 500 genérico sem vazar detalhe.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ATENDENTE_SVO, ADMINISTRADOR, GESTOR, SOLICITANTE, MOTORISTA, EQUIPE_SVO).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE na confirmação concorrente de ocorrências SVO.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

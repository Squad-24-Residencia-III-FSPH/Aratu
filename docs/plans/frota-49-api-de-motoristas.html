1. Contexto, Objetivo e Escopo

Disponibilizar ao Gestor e ao Administrador uma API para manter o cadastro de motoristas da FSPH/SVO e a situação de cada um, com histórico rastreável, servindo de base para o agendamento (US14, FROTA-96) e para o acesso do motorista às suas viagens (US15). Entra: cadastro, consulta, edição, mudança de situação, vínculo opcional com conta MOTORISTA e o método reutilizável de disponibilidade. Fica fora: exclusão física, telas React, escala/agenda e o endpoint GET /drivers/available (escopo da FROTA-96).

Decisões confirmadas com o usuário (Regra da Dúvida):

  • Qualquer situação pode ir para qualquer outra (ACTIVE, AWAY, INACTIVE); ir para ACTIVE exige CNH válida (422 se vencida).
  • Cadastro ou edição que deixaria um motorista ACTIVE com CNH vencida é recusado com 422; o cadastro aceita status inicial opcional (padrão ACTIVE).
  • Vínculo com usuário inexistente, inativo ou sem perfil MOTORISTA → 422; usuário já vinculado a outro motorista → 409; userId: null remove o vínculo.
  • Listagem sem paginação (igual a veículos), com filtro de nome parcial sem diferenciar maiúsculas e filtro de situação.

2. Requisitos e Regras de Negócio (Casos de Borda)

  • CPF: obrigatório, somente 11 dígitos (sem pontuação) e com dígitos verificadores válidos; sequências repetidas (ex.: 00000000000) são inválidas → 400. Dado um CPF já cadastrado, quando cadastrar ou editar outro motorista com ele, então 409 { "erro": "CPF já cadastrado" }. O índice único fleet_drivers_cpf_unique protege a corrida concorrente (23505 → 409).
  • CNH: número obrigatório (texto não vazio), categoria em A, B, C, D, E, AB, AC, AD, AE e validade YYYY-MM-DD obrigatória → 400 se ausente ou inválida. A CNH é válida até o dia da validade, inclusive; está vencida quando a validade é anterior à data corrente (fuso America/Maceio, Aracaju/SE).
  • Situação: dado um motorista com CNH vencida, quando o Gestor tentar deixá-lo ACTIVE (cadastro, edição ou PATCH), então 422. Mudar para a mesma situação retorna o registro sem novo evento.
  • Vínculo: userId opcional; deve apontar para usuário existente, ativo e de perfil MOTORISTA (422 caso contrário) e não pode estar vinculado a outro motorista (409; índice parcial fleet_drivers_user_id_unique).
  • Concorrência: PUT e PATCH exigem expectedRevision; revisão divergente → 409. Toda mutação exige reportedBy e reason (colunas obrigatórias de fleet.driver_events) e grava evento + audit.logs na mesma transação.
  • Disponibilidade: DriversService.isAvailableForAllocation(id) retorna true somente para ACTIVE com CNH não vencida; reutilizado pela FROTA-96.
  • Sem DELETE: o motorista é inativado. Telefone opcional (texto vazio vira null).

5. Back-end — Contratos REST e Detalhamento por Arquivo (Express 5 / TS)

Método e rotaAcessoContrato / resultado
GET /driversGESTOR, ADMINISTRADORFiltros opcionais name (parcial) e status; 200 lista ordenada por nome; 400 situação inválida.
GET /drivers/:idGESTOR, ADMINISTRADOR200 motorista; 400 id inválido; 404 se ausente.
POST /driversGESTOR, ADMINISTRADORname, cpf, cnhNumber, cnhCategory, cnhExpiresAt, phone?, userId?, status?, reportedBy, reason; 201; 400 / 409 / 422.
PUT /drivers/:idGESTOR, ADMINISTRADORMesmos atributos sem status, mais expectedRevision; 200; 400 / 404 / 409 / 422.
PATCH /drivers/:id/statusGESTOR, ADMINISTRADORstatus, expectedRevision, reportedBy, reason; 200; 400 / 404 / 409 / 422.

Resposta Driver: id, name, cpf, cnhNumber, cnhCategory, cnhExpiresAt (texto YYYY-MM-DD), phone, status, userId, revision, createdAt, updatedAt. Erros no formato { "erro": "..." } via DriverServiceError.

Camadas iguais à API de veículos: Route (JWT → authorizeRoles) → Controller (adapta HTTP) → DriversService (validações, regra de CNH, vínculo, orquestração de evento + auditoria) → DriversRepository (SQL parametrizado, projeção explícita, findByIdForUpdate com FOR UPDATE, withTransaction com release() no finally). O snapshot do ator é lido do banco na transação. O filtro de nome escapa %, _ e \ antes do ILIKE.

7. Acessibilidade (WCAG 2.2 Nível AA)

Sem interface nesta tarefa. Aplica-se apenas a clareza das mensagens de erro da API (3.3.1 / 3.3.3): cada 400/409/422 diz em português o que corrigir (ex.: "CNH vencida: renove a validade antes de deixar o motorista ativo."). Os itens abaixo valem para a futura tela.

  • Rótulos e Erros (1.3.1, 3.3.1, 3.3.2): Todos os campos usam useId() conectando <label htmlFor> ao <input id>, aria-invalid e mensagem de erro com role="alert".
  • Teclado e Foco Visível (2.1.1, 2.4.7, 2.4.11): Operável integralmente via Tab, Shift+Tab, Enter, Espaço e Esc, com :focus-visible nítido.
  • Tamanho do Alvo (2.5.8): Botões e controles interativos possuem área mínima de 44×44px em telas operacionais.
  • Contraste e Uso de Cor (1.4.1, 1.4.3, 1.4.11): Contraste de texto >= 4.5:1 e status acompanhado de rótulo textual além da cor.
  • Mensagens de Status (4.1.3): Feedbacks dinâmicos anunciados via role="status" ou aria-live="polite".

8. Escopo de Impacto, RBAC e Configuração

Leitura e escrita: somente GESTOR e ADMINISTRADOR; demais perfis (SOLICITANTE, MOTORISTA, ATENDENTE_SVO, EQUIPE_SVO) recebem 403; sem token, 401. Reutiliza createAuthMiddleware e authorizeRoles. Sem novas variáveis de ambiente. CPF e CNH são dados pessoais (LGPD): ficam restritos a esses perfis e nunca aparecem em logs de erro.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

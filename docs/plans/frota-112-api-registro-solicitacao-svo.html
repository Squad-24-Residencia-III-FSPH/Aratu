2. Requisitos e Regras de Negócio (Casos de Borda)

RegraDefinição implementável
Campos do chamadoStrings obrigatórias não vazias após trim: requesterName, requesterPhone, requesterType, location, description. notes opcional; vazio normalizado para null. Telefone é texto não vazio, sem impor máscara ou validação de DDD não solicitada.
Tipo do solicitanteFAMILY | HOSPITAL | UBS | UPA | PUBLIC_AGENCY | OTHER
Horário e origemreceivedAt opcional em ISO 8601 com Z ou offset explícito; data válida e não futura em relação ao instante da operação no banco. Omitido usa o instante do cadastro. evidenceDescription obrigatório, texto não vazio, descreve canal/meio; sem enum de canais ou campo de upload.
Estado inicialServidor fixa PENDING e revision = 1; attendantId e snapshot derivam da conta autenticada. Não aceitar propriedades de estado/autoria no corpo.
ConfirmarSomente PENDING; validar os campos obrigatórios armazenados, sem questionário adicional. Gravar CONFIRMED, triagedBy, triagedAt e incrementar revision sob FOR UPDATE. CONFIRMED/CANCELED → 409.
TrilhaCriação gera RECEIVED; confirmação gera CONFIRMED, sem duplicar com TRIAGED. Cada ato escreve entidade, evento e auditoria na mesma transação.
RepetiçãoConfirmação repetida ou concorrente não duplica efeito e retorna 409. Criação não tem chave natural nem chave de idempotência na estrutura atual: não fazer deduplicação por nome/telefone/local nem prometer replay seguro; consumidor não deve reenviar POST automaticamente após resposta incerta.
ListagemFiltros opcionais status, from e to; datas YYYY-MM-DD em America/Maceio, sobre received_at, intervalo semiaberto; ordenação received_at DESC, id DESC. Retorno array como listagem atual de viagens, sem paginação nova nesta entrega.

4. Banco de Dados e Migrações (PostgreSQL 18)

Não há nova migration nem alteração da migration já aplicada. Reutilizar schemas nativos, PK id BIGINT GENERATED ALWAYS AS IDENTITY, FKs ON DELETE RESTRICT e os índices existentes; a convenção canônica prevalece sobre exemplos antigos de prefixos de três letras.

DadoPersistência / compatibilidade
Chamado atualsvo.occurrences: dados da solicitação, status, received_at, attendant_id, attendant_snapshot, triaged_at/by, revision, created_at e updated_at.
Origem / evidênciasvo.occurrence_events.evidence_description no evento RECEIVED. No detalhe, ler o primeiro RECEIVED com ordenação registered_at, id; legado sem evento retorna null.
Bi-temporalidadeRECEIVED.occurred_at = received_at informado; registered_at automático do banco. Na confirmação, occurred_at e triaged_at refletem a confirmação executada no sistema. Não reescrever o received_at original.
Autoria e motivoCriação: reported_by = requester_name; registered_by = operador, actor_snapshot = { id, name, email, role }, reason fixo “Solicitação SVO recebida e registrada.”. Confirmação: reported_by = nome do operador, reason fixo “Triagem SVO conferida e solicitação confirmada.”; evidência descreve a conferência realizada na sessão autenticada.
Estado históricobefore_state/after_state da tabela de eventos guardam o contexto do domínio; dados pessoais ficam restritos ao schema SVO. Não copiar esses objetos para audit.logs.
LegadoNão preencher snapshots, canais ou horários retroativamente. Retornar null para evidência/snapshot ausente; manter estados existentes. Validar invariantes antes de confirmar.

Unidade transacional

BEGIN;
-- Capturar e travar conta ativa (FOR SHARE); conferir perfil atual.
-- Na confirmação, ler a ocorrência com FOR UPDATE e validar PENDING.
-- INSERT da ocorrência OU UPDATE do estado/revision.
-- INSERT em svo.occurrence_events (append-only).
-- AuditService.recordAudit(..., MESMO PoolClient).
COMMIT;
-- Qualquer falha: ROLLBACK; client.release() no finally.

Atualização de estado não apaga o passado: o evento anterior continua imutável. Sem DELETE ou UPDATE de eventos. Consultas nomeiam colunas e usam $1, $2; IDs são strings para não perder precisão de BIGINT. Filtros não aplicam DATE() na coluna. O índice svo_occurrences_by_status_received atende status + período; consultas sem status devem ser medidas com EXPLAIN antes de propor novo índice.

Rollback de entrega: reverter o código das novas rotas e a composição em app.ts, mantendo as tabelas e todos os dados/eventos. Não executar o .down.sql da FROTA-110, pois também sustenta o módulo SVO. Falhas de requisição fazem rollback transacional integral; testes isolados de Repository encerram com ROLLBACK.

DTO de criação

interface CreateSvoOccurrenceInput {
  requesterName: string
  requesterPhone: string
  requesterType: "FAMILY" | "HOSPITAL" | "UBS" | "UPA" | "PUBLIC_AGENCY" | "OTHER"
  location: string
  description: string
  notes?: string | null
  receivedAt?: string // ISO 8601 com fuso; omitido = instante do cadastro
  evidenceDescription: string // canal/meio do recebimento
}

JSON deve ser objeto; arrays, null, campos de tipo incorreto e propriedades fora do contrato retornam 400. A confirmação aceita ausência de corpo ou {}; id usa decimal positivo até 9223372036854775807. Status, carimbos de confirmação, revisão e snapshots são controlados pelo servidor.

Projeções de resposta

  • SvoOccurrenceSummary: id, requesterType, location, status, receivedAt, createdAt, revision. Não incluir telefone, descrição, notas ou snapshot do operador na lista.
  • SvoOccurrenceDetail: campos de Summary + requesterName, requesterPhone, description, notes, attendantId, triagedAt, triagedBy, updatedAt e evidenceDescription (nullable para legado). Não expor snapshots brutos nem eventos completos no contrato.
  • Datas de resposta serializadas em ISO 8601; ids/FKs como strings; revision como inteiro. A leitura autorizada do GESTOR usa as mesmas projeções documentadas.
  • status aceita PENDING, CONFIRMED ou CANCELED. from/to opcionais e inclusivos por dia local; converter limites para instantes antes do SQL, usando >= início e < dia seguinte ao fim. Rejeitar query array/objeto, data impossível e intervalo invertido.

Responsabilidades por camada

  • Routes: createAuthMiddleware → createCurrentUserMiddleware → authorizeRoles → controller; leituras autorizam ATENDENTE_SVO/ADMINISTRADOR/GESTOR, escritas apenas ATENDENTE_SVO/ADMINISTRADOR. Exportar handler de erros com quatro argumentos para montagem por caminho em app.ts, depois das rotas SVO e antes do handler global. Assim também são alcançados erros do parser JSON executado antes do router, além das falhas de middleware/repository.
  • Controller: obter id/query/body/req.usuario.id, validar forma HTTP, chamar service e traduzir resultado para JSON. Erros previstos usam { erro: mensagem }; mensagens de domínio não reproduzem dados enviados.
  • Service: createOccurrence, listOccurrences, getOccurrence e confirmOccurrence; receber repository e AuditLogger por construtor; sem importar Express. Validar datas, textos, FSM, conta/perfil e compor evento/auditoria.
  • Repository: withTransaction, findActorSnapshot, create, list, findById, findByIdForUpdate, confirm e createEvent. findActorSnapshot usa conta ativa com FOR SHARE; escritas revalidam o perfil real antes de persistir. findById busca a evidência original sem N+1 na listagem.
  • Concorrência: em confirmOccurrence, trava da conta e da ocorrência em ordem consistente; obter o estado dentro do lock, validar, atualizar e gravar trilha antes do commit. Retorno só após commit.

Detalhes para implementação sem divergência de contrato

  • Erros de domínio: definir códigos semânticos tipados para entrada inválida, conta indisponível, acesso negado, ocorrência inexistente e transição inválida; o controller/handler traduz para 400/401/403/404/409. O service não importa Express nem depende de objetos HTTP.
  • Relógio: o repository fornece o instante do banco dentro da transação. O service compara receivedAt com esse instante; quando omitido, usa esse mesmo valor. Na confirmação, persistir uma única referência temporal em triaged_at e CONFIRMED.occurred_at; registered_at continua automático. Validar calendário e fuso antes de converter para Date, sem aceitar normalização silenciosa de datas impossíveis.
  • Observações: notes omitido, null, vazio ou só espaços resulta em null; outros tipos retornam 400. Não enviar texto vazio à constraint do banco.
  • Legado: ausência de evidência de recebimento ou snapshot histórico permanece null e não impede, por si só, a confirmação simples dos campos obrigatórios do chamado. Não inventar autoria passada nem retropreencher o evento RECEIVED.
  • Resultado incerto: consultar ajuda na conferência operacional, mas sem chave de idempotência não comprova por si só qual POST originou um registro. Não oferecer reenvio automático nem deduplicação por dados pessoais; mantém-se a limitação já registrada neste escopo.

Auditoria e falhas sem vazamento

AuditService.sanitizeSnapshot remove senhas, mas não remove os dados sensíveis do SVO. Portanto criar projeção local explícita para audit.logs: before/after apenas { id, status, revision, receivedAt, triagedAt, triagedBy }; actorSnapshot contém a autoria autenticada, nunca a identidade do solicitante. operation = CREATE ou STATUS_CHANGE; reason é texto fixo. Não enviar requesterName, requesterPhone, location, description, notes ou evidenceDescription, nem estruturas aninhadas que os contenham.

O handler global atual registra o erro completo; o parser express.json() é instalado antes dos routers. Montar app.use('/svo/occurrences', svoErrorHandler) depois das rotas e antes do handler global (um handler apenas dentro do router não cobre falhas anteriores à entrada nele). Preservar 400 e a mensagem existente para JSON malformado, sem reproduzir o corpo recebido. Para falhas inesperadas das novas rotas SVO, interceptar antes do handler global e registrar somente código técnico controlado, operação e instante; não registrar objeto Error bruto, message/detail/stack SQL, req.body, parâmetros livres ou token. Resposta 500: “Não foi possível concluir a operação. Consulte as solicitações antes de tentar novamente.”. Manter comportamento dos outros módulos.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ATENDENTE_SVO, ADMINISTRADOR, GESTOR, SOLICITANTE, MOTORISTA, EQUIPE_SVO).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE na confirmação concorrente de ocorrências SVO.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

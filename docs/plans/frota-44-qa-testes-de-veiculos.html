1. Contexto, Objetivo e Escopo

Comprovar, por testes automatizados de integração, que o gerenciamento de veículos da frota da FSPH/SVO (US04) respeita os critérios das FROTA-43 e FROTA-45: cadastro e edição rastreáveis, unicidade da placa, filtros, máquina de estados da situação, concorrência, disponibilidade para alocação e RBAC. A entrega dá à Squad confiança para evoluir agendamento, SVO e manutenção sobre uma base já validada.

Entra no escopo: novo backend/tests/vehicles.integration.test.ts, cobrindo API REST, PostgreSQL 18, auditoria, histórico append-only, RBAC e isAvailableForAllocation. Fica fora: telas React da FROTA-46 (outra equipe, apenas contexto), novos endpoints, migrations e alterações de regra de negócio.

Auditoria dos concluídos: FROTA-43 e FROTA-45 estão conformes no código atual; não há mudança obrigatória em produção. Decisões confirmadas pela Regra da Dúvida: (1) manter o contrato expectedRevision e documentá-lo; (2) incluir casos extras de concorrência, idempotência e atomicidade; (3) validar disponibilidade instanciando o VehiclesService real no teste, sem criar endpoint novo.

2. Requisitos e Regras de Negócio (Casos de Borda)

Requisitos funcionais (Dado / Quando / Então)

  • Dado um gestor autenticado, quando cadastra veículo com placa válida, então recebe 201, status=AVAILABLE, revision=1, evento CREATED e auditoria CREATE.
  • Dado placa ABC-1234, AB1234 ou ABC12345, quando cadastra, então recebe 400.
  • Dado veículo ABC1D23, quando cadastra abc1d23, então recebe 409 com { "erro": "Placa já cadastrada" }.
  • Dado ID inexistente, quando consulta, então recebe 404 com { "erro": "Veículo não encontrado." }; ID malformado retorna 400.
  • Dado filtro ?status=IN_MAINTENANCE, quando lista, então retorna somente veículos nesse estado; filtro inválido retorna 400.
  • Dado edição com expectedRevision atual, então 200, revision+1, evento UPDATED e auditoria UPDATE; revisão antiga retorna 409.
  • Dado as transições AVAILABLE → IN_MAINTENANCE → INACTIVE → AVAILABLE, então 200; INACTIVE → IN_MAINTENANCE retorna 422; repetir o mesmo status é idempotente.
  • Dado isAvailableForAllocation, então true apenas para AVAILABLE; false para IN_MAINTENANCE e INACTIVE; ID ausente resulta em erro 404.
  • Dado perfil SOLICITANTE, então 403 na leitura e escrita; ATENDENTE_SVO lê (200), mas não escreve (403); sem token retorna 401.

Requisitos não-funcionais e casos de borda

  • Concorrência: duas edições simultâneas com a mesma revision resultam em exatamente uma 200 e uma 409, graças a SELECT ... FOR UPDATE + incremento de revision.
  • Atomicidade: falha de domínio não deixa evento em fleet.vehicle_events nem log em audit.logs; ator inativado faz rollback integral.
  • Isolamento: cada teste roda com banco truncado, roles e usuários RBAC fictícios; nenhum dado pessoal real (LGPD/SVO).

4. Banco de Dados e Migrações (PostgreSQL 18)

Não se aplica. A FROTA-44 é uma tarefa de QA e não cria nem altera schema. A suíte usa as migrations já existentes:

  • 202610210001_create_vehicles.sql: fleet.vehicles e fleet.vehicle_events, constraints de domínio e trigger append-only.
  • 202610280001_alter_vehicles_add_details.sql: brand, model, year, vehicle_type, ownership e unicidade em upper(license_plate).
  • auth.users, auth.roles e audit.logs para RBAC e auditoria.

Plano de rollback: não há DDL a reverter. O isolamento é feito por truncateTestDatabase() antes de cada teste, preservando schemas e reiniciando identidades. Se a suíte falhar no meio, o próximo beforeEach restaura o estado limpo.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

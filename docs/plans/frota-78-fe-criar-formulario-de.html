1. Contexto, Objetivo e Escopo

Permitir que o servidor autenticado com perfil SOLICITANTE na Fundação de Saúde Parreiras Horta (FSPH) solicite uma viagem institucional por meio de uma página dedicada (RequestTripPage.tsx em /solicitacoes/nova), consultando os tipos de serviço ativos na API real (GET /services) e enviando a solicitação para POST /requests via createApiClient. Ao concluir o envio com sucesso (201 Created com { id, status: "PENDING" }), a interface exibe a confirmação "Solicitação registrada", sincroniza o registro criado na listagem em memória do solicitante e redireciona para "Minhas solicitações" (/solicitacoes/minhas), onde a nova solicitação aparece imediatamente com status Pendente.

Delimitação de Escopo (YAGNI)

  • Entra no escopo (FROTA-78 / US11 Front-end):
    • Criação da página dedicada frontend/src/pages/RequestTripPage.tsx na rota protegida /solicitacoes/nova (exclusiva para SOLICITANTE);
    • Utilização dos componentes padronizados PageHeader, FormField (incluindo suporte a type="time"), FormSelect e StateFeedback;
    • Cliente de API tipado frontend/src/services/requestsService.ts para GET /services (carregamento de tipos de serviço ativos) e POST /requests (criação da solicitação);
    • Tipagens, regras de acesso, validação de conforto de formulário e armazenamento de sessão das solicitações criadas em frontend/src/requests/;
    • Unificação das rotas do perfil SOLICITANTE em routeDecision.ts, sidebarNavigation.ts e App.tsx (/solicitacoes/minhas e /solicitacoes/nova, mantendo compatibilidade de redirecionamento de /minhas-solicitacoes para /solicitacoes/minhas) e sincronização com SolicitacaoPage.tsx;
    • Testes automatizados unitários e de renderização/fluxo em frontend/tests/.
  • Fora do escopo (Com marcação explícita TODO no código para futuras tasks):
    • Alterações no backend Express ou banco PostgreSQL 18 (o backend de POST /requests já foi entregue em FROTA-79/FROTA-80);
    • Implementação do endpoint backend GET /requests (pertence à subtarefa FROTA-82 da FROTA-81 — US12 Consultar solicitação) e refatoração completa da tabela de consulta de SolicitacaoPage.tsx (FROTA-84). Todos os pontos de transição entre o armazenamento local de solicitações recém-criadas e a futura API GET /requests serão documentados com comentários explícitos // TODO(FROTA-82/FROTA-84): ... no código.

Decisões Confirmadas pela Regra da Dúvida

  1. Contrato de campos do formulário: Manter estritamente os 6 campos do contrato de POST /requests (FROTA-79): data da viagem (requestedDate), horário de saída (requestedTime), tipo de serviço (serviceId populado via GET /services), origem (origin), destino (destination) e finalidade (purpose), sem alterar o backend.
  2. Estrutura de tela e rota: Criar página dedicada RequestTripPage.tsx em /solicitacoes/nova conectada ao item "Nova Solicitação" da Sidebar do Solicitante e ao botão "Nova Solicitação" da página "Minhas Solicitações", redirecionando para /solicitacoes/minhas após o envio bem-sucedido.
  3. Sincronização com "Minhas Solicitações" antes de FROTA-82: Ao receber 201 { id, status: "PENDING" } de POST /requests, registrar a solicitação recém-criada em um store/sessão compartilhado no front-end e exibi-la como Pendente no topo de SolicitacaoPage.tsx, deixando comentários claros (TODO(FROTA-82)) indicando onde substituir pela leitura de GET /requests quando a US12 for integrada.
  4. Identificação do SDD e branch: Vincular à subtarefa de Front-end FROTA-78 (docs/plans/frota-78-fe-criar-formulario-de.html e branch feat/frota-78-formulario-solicitacao-viagem).

2. Requisitos e Regras de Negócio (Casos de Borda)

Dado Quando Então
SOLICITANTE autenticado acessa /solicitacoes/nova e existem tipos de serviço ativos A página inicializa Busca GET /services via api/client.ts, exibe estado de carregamento acessível e popula o seletor "Tipo de serviço" com os serviços ativos.
SOLICITANTE preenche data futura, horário válido, tipo de serviço, origem, destino e finalidade Submete o formulário clicando em "Solicitar viagem" Desabilita o botão com indicador de envio, envia POST /requests, recebe 201 { id, status: "PENDING" }, registra o alerta de sucesso "Solicitação registrada", adiciona o item como Pendente na lista de "Minhas solicitações" e redireciona para /solicitacoes/minhas.
Usuário submete formulário com campos obrigatórios vazios, data inválida ou horário fora de HH:mm Tenta enviar o formulário Bloqueia o envio HTTP, exibe mensagens de erro por campo via FormField/FormSelect (com aria-invalid="true" e role="alert") e move o foco para o primeiro campo inválido.
API POST /requests responde 400 ou 422 com { erro: "..." } (ex: data/hora no passado ou serviço inativo) Recebe resposta de erro da API Mantém os dados digitados no formulário, reabilita o botão de envio e exibe a mensagem exata do campo erro da API em um Alert com role="alert"; nunca exibe sucesso nem redireciona.
Backend fora do ar ou falha de rede/timeout em GET /services ou POST /requests O createApiClient lança SERVICE_UNAVAILABLE Exibe a mensagem "Serviço temporariamente indisponível" com opção de tentar novamente (no carregamento de serviços) ou preserva o formulário preenchido (no envio).
Catálogo GET /services retorna lista vazia ([]) A página conclui o carregamento Exibe StateFeedback de estado vazio orientando que não há tipos de serviço ativos disponíveis para solicitação no momento.
Usuário não autenticado ou com perfil diferente de SOLICITANTE Tenta acessar /solicitacoes/nova ou /solicitacoes/minhas resolveRoute redireciona para /login (se sem sessão/expirado) ou para a home do respectivo perfil RBAC.
Nota para Desenvolvedores e Agentes de IA (Pontos Abertos de Tarefas Futuras):
  • FROTA-82 / FROTA-84 (US12 — Consultar solicitação): O endpoint GET /requests ainda não está na develop. Por isso, as solicitações criadas via POST /requests são sincronizadas pelo módulo frontend/src/requests/createdRequestsStore.ts para exibição imediata em SolicitacaoPage.tsx. Quando FROTA-82 for mergeada, basta conectar listRequests em requestsService.ts (marcada com TODO(FROTA-82)) e remover os mocks residuais de SolicitacaoPage.tsx.
  • Campo passengers (Nº de passageiros): Caso a Squad decida futuramente expor passengers no payload de POST /requests (a coluna já existe em trip.requests com default 1), o DTO CreateTripRequestInput em requestTypes.ts contém comentário indicando o ponto exato de extensão.

Tratamento dos 5 Estados Visuais

Estado Visual Comportamento na Tela (RequestTripPage.tsx e SolicitacaoPage.tsx)
1. Ideal Formulário renderizado com tipos de serviço ativos carregados no FormSelect e campos Data da viagem, Horário de saída, Tipo de serviço, Origem, Destino e Finalidade. Após envio válido, redireciona para /solicitacoes/minhas exibindo alerta de sucesso "Solicitação registrada" (role="status") e a solicitação no topo da tabela com status Pendente.
2. Carregando (Loading)
  • Ao abrir a tela: StateFeedback kind="loading" title="Carregando tipos de serviço..." com role="status" e aria-busy="true" enquanto GET /services está em curso.
  • Durante o envio (POST /requests): Botão de submissão e controles desabilitados com CircularProgress size={18} e rótulo "Enviando solicitação..." para impedir cliques duplicados (idempotência de UI).
3. Vazio (Empty State) Quando GET /services retorna zero serviços ativos, exibe StateFeedback kind="empty" title="Nenhum tipo de serviço disponível" description="Não há tipos de serviço ativos para registrar uma solicitação no momento." actionLabel="Atualizar".
4. Erro
  • Falha ao carregar GET /services: StateFeedback kind="error" exibindo a mensagem da API ou "Serviço temporariamente indisponível" com botão "Tentar novamente".
  • Falha ao enviar POST /requests: Alert severity="error" role="alert" no topo do formulário exibindo a mensagem do campo erro da API (ou "Serviço temporariamente indisponível" quando offline), preservando 100% dos campos preenchidos pelo usuário.
5. Parcial Em SolicitacaoPage.tsx, exibe as solicitações recém-criadas na API real (POST /requests) mescladas à listagem local enquanto o endpoint de consulta GET /requests (FROTA-82) não está publicado na develop, sinalizando em código com TODO(FROTA-82/FROTA-84) o ponto exato de substituição.

7. Acessibilidade (WCAG 2.2 Nível AA)

  • Rótulos e Erros (1.3.1, 3.3.1, 3.3.2): Todos os 6 campos (requestedDate, requestedTime, serviceId, origin, destination, purpose) usam FormField / FormSelect com useId() conectando <label htmlFor> ao <input id>, aria-invalid e mensagem de erro com role="alert".
  • Teclado e Foco Visível (2.1.1, 2.4.7, 2.4.11): Operável integralmente via Tab, Shift+Tab, Enter e Espaço, com redirecionamento automático de foco (inputRef) para o primeiro campo com erro ao validar.
  • Tamanho do Alvo (2.5.8): Botões "Solicitar viagem", "Cancelar" e "Nova Solicitação" possuem altura mínima de 44px (definida no tema e reforçada em sx={{ minHeight: 44 }}).
  • Contraste e Uso de Cor (1.4.1, 1.4.3, 1.4.11): Contraste de texto >= 4.5:1 e status Pendente acompanhado de rótulo textual explícito além da cor.
  • Mensagens de Status (4.1.3) e Entrada Não Redundante (3.3.7): Confirmação "Solicitação registrada" anunciada via role="status" / aria-live="polite"; em caso de erro da API, nenhum campo preenchido pelo usuário é perdido.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

1. Contexto, Objetivo e Escopo

1.1 Objetivo e Contexto Operacional

Permitir que o Solicitante acompanhe as suas solicitações de transporte institucional e que o Gestor e o Administrador consultem todas as solicitações da FSPH, com filtros por situação e período, paginação e detalhe com os dados da viagem quando houver agendamento. A consulta é somente leitura e não altera o ciclo de vida da solicitação.

1.2 Delimitação de Escopo (YAGNI)

Entra no escopoFica fora do escopo
  • GET /requests com status, from, to, page e pageSize.
  • GET /requests/:id com detalhe e dados da viagem.
  • Estrutura do módulo: types, repositories, services, controllers e routes.
  • Escopo por perfil no service e RBAC na rota.
  • Testes unitários e de integração.
  • POST /requests e criação de solicitações (FROTA-79).
  • Aprovação, recusa, cancelamento e agendamento.
  • Tela de acompanhamento (FROTA-84).
  • Auditoria de leitura em audit.logs.
  • Uso de requester_snapshot/service_snapshot.
  • Filtro por requesterId para o Gestor.
  • Migração de banco: as tabelas da FROTA-77 já existem.

1.3 Decisões Confirmadas (Regra da Dúvida)

  1. A FROTA-82 cria a base de leitura do módulo; a FROTA-79 acrescenta o POST depois.
  2. Status em inglês UPPER_SNAKE_CASE: PENDING, APPROVED, REJECTED, SCHEDULED, CANCELED.
  3. Período sobre requested_date, inclusivo, no formato YYYY-MM-DD; from > to retorna 400.
  4. Listagem com resumo + nomes de solicitante/serviço e paginação page/pageSize (default 20, máximo 100).
  5. SOLICITANTE vê apenas as próprias; GESTOR/ADMINISTRADOR veem todas; MOTORISTA recebe 403; detalhe de outra pessoa retorna 404; SCHEDULED sem linha em trip.trips retorna trip: null.
  6. Snapshots históricos não são usados nesta entrega; os nomes vêm de JOIN com os dados atuais.

2.3 Regras de Validação

  • Situação: apenas os cinco valores do banco; qualquer outro retorna 400.
  • Datas: from e to opcionais, formato exato YYYY-MM-DD e data de calendário válida; from > to retorna 400.
  • Paginação: page inteiro >= 1; pageSize inteiro entre 1 e 100; default page=1, pageSize=20.
  • ID: apenas dígitos positivos (^[1-9]\\d*$); inválido retorna 400.
  • Escopo: o service nunca confia em requesterId vindo do cliente; usa o id do token.
  • Leitura: não altera estado nem grava auditoria.

2.4 Requisitos Não-Funcionais

  • Segurança: autenticação JWT e autorização RBAC em todas as rotas; queries parametrizadas.
  • Desempenho: filtros e ordenação no PostgreSQL; paginação com LIMIT/OFFSET; sem N+1 no detalhe.
  • Compatibilidade: nenhum endpoint existente é alterado; contrato novo sob /requests.
  • LGPD: nenhum dado pessoal real em testes ou fixtures.

4. Banco de Dados e Migrações (PostgreSQL 18)

4.1 Situação Atual do Schema

As tabelas necessárias já existem nas migrations 202610280004_create_trip_requests.sql e 202610280005_create_trips.sql:

  • trip.requests — id, requester_id, service_id, requested_date, requested_time, origin, destination, purpose, passengers, status, decided_by, decided_at, decision_reason, revision, created_at, updated_at.
  • trip.trips — request_id (UNIQUE), vehicle_id, driver_id, scheduled_start, scheduled_end, status.
  • fleet.vehicles — id, license_plate, brand, model.
  • fleet.drivers — id, name.
  • auth.users — id, name.

4.2 Migração

Não se aplica a esta tarefa. Nenhuma tabela, coluna, constraint ou índice é criado. Como não há DDL, não há plano de rollback a executar.

4.3 Índices Existentes e Plano de Consulta

ConsultaÍndice existenteSituação
SOLICITANTE + ordenação por datatrip_requests_by_requester (requester_id, created_at DESC, id DESC)Filtra pelo solicitante; a ordenação por requested_date ocorre sobre o conjunto já reduzido.
GESTOR + situação + períodotrip_requests_by_status_date (status, requested_date, requested_time, id)Cobre o filtro principal.
GESTOR apenas por períodoNenhum índice com requested_date como primeira colunaPode gerar Seq Scan em volume alto.

Decisão: não criar índice especulativo. Após a implementação, executar EXPLAIN (ANALYZE, BUFFERS) com volume representativo. Se o filtro apenas por período degradar, abrir uma migration de acompanhamento com trip_requests_by_requested_date (requested_date DESC, requested_time DESC, id DESC) e rollback DROP INDEX.

4.4 Consultas Previstas

Listagem

SELECT r.id::text AS id,
       r.requester_id::text AS "requesterId",
       u.name AS "requesterName",
       r.service_id::text AS "serviceId",
       s.name AS "serviceName",
       to_char(r.requested_date, 'YYYY-MM-DD') AS "requestedDate",
       to_char(r.requested_time, 'HH24:MI') AS "requestedTime",
       r.origin,
       r.destination,
       r.purpose,
       r.passengers,
       r.status,
       r.created_at AS "createdAt",
       r.updated_at AS "updatedAt"
  FROM trip.requests r
  JOIN auth.users u ON u.id = r.requester_id
  JOIN fleet.services s ON s.id = r.service_id
 WHERE ($1::text IS NULL OR r.status = $1)
   AND ($2::date IS NULL OR r.requested_date >= $2::date)
   AND ($3::date IS NULL OR r.requested_date <= $3::date)
   AND ($4::bigint IS NULL OR r.requester_id = $4::bigint)
 ORDER BY r.requested_date DESC, r.requested_time DESC, r.id DESC
 LIMIT $5 OFFSET $6;

O detalhe usa um único SELECT com LEFT JOIN para evitar N+1. requestedDate sai como YYYY-MM-DD, requestedTime como HH:MM e os timestamps de viagem em ISO 8601 (UTC).

5.2 backend/src/types/request.types.ts

export const REQUEST_STATUSES = [
  'PENDING', 'APPROVED', 'REJECTED', 'SCHEDULED', 'CANCELED',
] as const
export type RequestStatus = typeof REQUEST_STATUSES[number]

export interface RequestListFilters {
  status?: RequestStatus
  from?: string
  to?: string
  page?: number
  pageSize?: number
}

export interface RequestSummary {
  id: string
  requesterId: string
  requesterName: string
  serviceId: string
  serviceName: string
  requestedDate: string
  requestedTime: string
  origin: string
  destination: string
  purpose: string
  passengers: number
  status: RequestStatus
  createdAt: string
  updatedAt: string
}

export interface RequestTrip {
  id: string
  status: string
  scheduledStart: string
  scheduledEnd: string
  vehicle: { id: string; licensePlate: string; brand: string | null; model: string | null }
  driver: { id: string; name: string }
}

export interface RequestDetail extends RequestSummary {
  decidedBy: string | null
  decidedByName: string | null
  decidedAt: string | null
  decisionReason: string | null
  trip: RequestTrip | null
}

export interface PaginatedRequests {
  requests: RequestSummary[]
  total: number
  page: number
  pageSize: number
  totalPages: number
}

export class RequestServiceError extends Error {
  readonly statusCode: number
  constructor(statusCode: number, message: string) {
    super(message)
    this.name = 'RequestServiceError'
    this.statusCode = statusCode
  }
}

RequestTrip.status fica como string nesta entrega porque o escopo é somente leitura e o módulo de viagens ainda não expõe uma união tipada própria. Não criar antecipadamente (YAGNI). brand e model são anuláveis porque as colunas de fleet.vehicles permitem NULL; a viagem continua sendo retornada quando a linha em trip.trips existe, mesmo que esses atributos não tenham sido informados.

5.3 backend/src/repositories/requests.repository.ts

  • Contrato:
    • list(filters: RequestListFilters & { requesterId?: string }): Promise<PaginatedRequests>
    • findById(id: string, requesterId?: string): Promise<RequestDetail | null>
  • Implementação com pg.Pool, queries parametrizadas, projeções explícitas e id::text.
  • list executa COUNT(*) e a página; converte total com parseInt.
  • findById recebe requesterId opcional; quando informado, aplica AND r.requester_id = $2 (404 natural para outro solicitante).
  • Mapeia a linha plana para RequestDetail, montando trip aninhado ou null.
  • Sem regra de negócio; apenas persistência e mapeamento.

5.4 backend/src/services/requests.service.ts

  • Construtor recebe RequestsRepositoryContract.
  • listRequests(filters, actor: { id: string; role: UserRole }):
    • valida situação com REQUEST_STATUSES;
    • valida from/to (formato + data real + ordem);
    • valida page/pageSize;
    • define requesterId = actor.role === 'SOLICITANTE' ? actor.id : undefined;
    • delega ao repositório.
  • getRequest(id, actor):
    • valida id;
    • define o mesmo escopo;
    • chama findById; se null, lança RequestServiceError(404, 'Solicitação não encontrada.').
  • Não importa Request/Response do Express.
  • Não reimplementa RBAC de perfil; aplica o escopo de dados exigido pelo card.

5.5 controllers, routes e app.ts

  • Controller: helpers queryText/queryNumber; monta RequestListFilters; repassa req.usuario.id e perfil; respondWithDomainErrors converte RequestServiceError em { erro }.
  • Routes: 
    const READ_ROLES = ['SOLICITANTE', 'GESTOR', 'ADMINISTRADOR'] as const

router.get('/', authenticate, authorizeRoles(READ_ROLES), controller.list)
router.get('/:id', authenticate, authorizeRoles(READ_ROLES), controller.getById)
  • app.ts: instanciar RequestsRepository(pool) e RequestsService(repo); montar app.use('/requests', createRequestsRouter(requestsService, jwtConfig)) dentro de if (pool). Não injetar AuditService, pois leitura não audita.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

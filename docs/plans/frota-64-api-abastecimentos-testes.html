1. Contexto, Objetivo e Escopo

Permitir que o Gestor e o Administrador registrem, consultem e retifiquem abastecimentos da frota FSPH/SVO, com controle de litros, gasto, posto e quilometragem e preservação integral do histórico.

Entrega delimitada: este SDD cobre somente FROTA-64 — API e FROTA-65 — testes automatizados, sob a história FROTA-62. A FROTA-66 — interface será executada por outra pessoa e não compõe esta implementação.

2.2 Histórico e precisão

Correções autorizadas após a revisão, em 06/11/2026: preservar os microssegundos de fueledAt no legado e nas retificações que omitem a data; aceitar até seis casas nos instantes e filtros, normalizando UTC sem perda e comparando a cronologia com precisão de microssegundos. Resolver currentId pela única ponta sem sucessora, sem pressupor revisões crescentes em cadeias legadas. As três falhas da revisão R1–R3 recebem testes de regressão; RBAC, histórico append-only e escopo sem frontend permanecem conforme as decisões registradas.

Cada versão registra o quê, quando ocorreu, quando foi registrado, quem informou, quem cadastrou, justificativa e evidência. fueledAt representa o fato; registeredAt vem do banco. Autor e snapshots são obtidos no servidor. Nenhum payload pode forjar autoria, supersedesId, revision, timestamps de registro ou isAnnulled.

Litros são decimais exatos com até 3 casas e valor em reais com até 2, transmitidos como strings decimais. Rejeitar excesso de escala/faixa, vírgula, notação científica e valores não finitos; não arredondar silenciosamente. IDs BIGINT são strings; quilometragem é inteiro de 0 a 2.147.483.647.

Não condicionar lançamentos históricos ao status atual do veículo ou motorista: validar existência, sem alterar disponibilidade, CNH, escalas ou status de manutenção. Não impor compatibilidade de combustível não prevista no cadastro. Não há novo parâmetro de configuração nem feature flag.

4. Banco de Dados e Migrações (PostgreSQL 18)

4.1 Estrutura existente e preservação

Prevalece a nomenclatura canônica atual de schemas nativos sobre exemplos antigos de prefixos de três letras presentes em material operacional.

4.2 Migração complementar planejada

As duas colunas novas são nulas para registros legados. As novas mutações da API sempre preenchem ambas. request_payload contém a entrada normalizada, tipo da operação e ID alvo, sem token, para comparar reenvios; a resposta pode ser reconstruída pela versão imutável gravada. Não inventar metadados para registros antigos.

BEGIN;
LOCK TABLE fleet.fuelings IN SHARE ROW EXCLUSIVE MODE;
DO $$
BEGIN
  IF EXISTS (
    SELECT supersedes_id FROM fleet.fuelings
    WHERE supersedes_id IS NOT NULL
    GROUP BY supersedes_id HAVING count(*) > 1
  ) THEN
    RAISE EXCEPTION 'Há retificações ramificadas. Revise o histórico antes de migrar.';
  END IF;
END;
$$;

ALTER TABLE fleet.fuelings
  ADD COLUMN request_key UUID,
  ADD COLUMN request_payload JSONB,
  ADD CONSTRAINT fleet_fuelings_request_pair CHECK (
    (request_key IS NULL AND request_payload IS NULL) OR
    (request_key IS NOT NULL AND request_payload IS NOT NULL
      AND jsonb_typeof(request_payload) = 'object')
  );

CREATE UNIQUE INDEX fleet_fuelings_request_key
  ON fleet.fuelings (created_by, request_key)
  WHERE request_key IS NOT NULL;
CREATE UNIQUE INDEX fleet_fuelings_one_successor
  ON fleet.fuelings (supersedes_id)
  WHERE supersedes_id IS NOT NULL;

CREATE FUNCTION fleet.prevent_fueling_mutation()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'Abastecimentos são imutáveis. Registre uma retificação.';
END;
$$;
CREATE TRIGGER fleet_fuelings_append_only
  BEFORE UPDATE OR DELETE ON fleet.fuelings
  FOR EACH ROW EXECUTE FUNCTION fleet.prevent_fueling_mutation();
COMMIT;

O índice por supersedes_id já existente não precisa ser removido nesta entrega. Reaproveitar os índices por veículo/data, motorista/data, eventos por abastecimento e leituras por veículo/data. Filtros temporais usam comparações diretas, sem DATE(coluna). Só adicionar índices de performance após medir com EXPLAIN (ANALYZE, BUFFERS), em dados fictícios representativos.

4.3 Rollback obrigatório

Antes do uso operacional, a reversão pode remover apenas os objetos adicionados. Depois de qualquer operação da nova API, reverter somente a aplicação, preservando schema e histórico. Nunca executar a down original da FROTA-63 para desfazer esta entrega: ela remove tabelas e vínculos compartilhados.

BEGIN;
LOCK TABLE fleet.fuelings IN ACCESS EXCLUSIVE MODE;
DO $$
BEGIN
  IF EXISTS (SELECT id FROM fleet.fuelings
             WHERE request_key IS NOT NULL OR request_payload IS NOT NULL) THEN
    RAISE EXCEPTION 'Rollback recusado para preservar histórico. Reverta apenas a aplicação.';
  END IF;
END;
$$;
DROP TRIGGER fleet_fuelings_append_only ON fleet.fuelings;
DROP FUNCTION fleet.prevent_fueling_mutation();
DROP INDEX fleet.fleet_fuelings_one_successor;
DROP INDEX fleet.fleet_fuelings_request_key;
ALTER TABLE fleet.fuelings
  DROP CONSTRAINT fleet_fuelings_request_pair,
  DROP COLUMN request_key,
  DROP COLUMN request_payload;
COMMIT;

O DatabaseMigrator já controla transação e versão da migração. Nenhum backfill de autoria, snapshots, evidências ou horários será feito. Versões antigas com campos nulos continuam consultáveis como informação não registrada. Cadeias cíclicas, ramificadas ou vínculos inconsistentes devem gerar diagnóstico e impedir a mutação afetada, sem “conserto” destrutivo automático.

5.3 Histórico completo, sem substituição destrutiva

  1. POST insere uma versão raiz revision=1, evento RECORDED, leitura FUELING com fueling_id e auditoria CREATE. Todos usam o mesmo ator autenticado e cliente transacional.
  2. PUT insere nova linha fleet.fuelings, supersedes_id = alvo.id, revision = alvo.revision + 1; nunca executa UPDATE no fato original. Evento RECTIFIED da nova versão contém before_state da anterior e after_state da nova, razão, evidência, informante e ator.
  3. Insere nova leitura FUELING vinculada à nova versão. supersedes_id aponta para a leitura vigente da versão anterior; inclusive alterações apenas de posto mantêm uma cadeia explícita de leituras, sem duplicação na visão vigente. Se o legado nunca teve leitura vinculada, iniciar uma leitura sem inventar o registro antigo.
  4. Auditoria UPDATE usa table=fleet.fuelings, recordId do novo registro e snapshots antes/depois contendo ambos os IDs. A operação é correção de negócio, embora fisicamente use INSERT.
  5. Preservar snapshots anteriores. Para a nova versão, reutilizar o snapshot histórico do veículo e do motorista quando a identidade não mudou; se houver alteração de motorista, capturar o novo vínculo sem modificar o antigo. Snapshot do autor sempre corresponde ao responsável por aquela mutação. Snapshot ausente no legado permanece desconhecido, sem alegar reconstrução histórica.
  6. Consulta do detalhe percorre a cadeia desde a raiz, traz versões e eventos com ordenação por registered_at/id e exibe também o instante do fato. Usar proteção contra ciclos no CTE recursivo. O histórico não depende dos dados cadastrais atuais para reconstruir nomes, autoria ou valores antigos.

Uma linha é vigente quando NOT EXISTS (SELECT id FROM fleet.fuelings next WHERE next.supersedes_id = current.id) e não está anulada. Verificar a existência de sucessor antes de filtrar a anulação: um sucessor anulado não deve ressuscitar o original. Aplicar a mesma regra às leituras. Nenhum DELETE é exposto.

5.4 Validação cronológica e dados legados

  1. Obter as leituras vigentes e não anuladas de trip.odometer_readings do veículo, incluindo abastecimentos/viagens e leituras operacionais já existentes.
  2. Complementar a linha do tempo com abastecimentos vigentes sem qualquer leitura vinculada e com start_km/started_at e end_km/finished_at de viagens sem trilha correspondente. Não somar a coluna antiga quando existir trilha START/END, mesmo retificada ou anulada: a trilha é a fonte autoritativa. Não usar datas agendadas como datas reais.
  3. Na correção, excluir a cadeia do fato corrigido e suas leituras do conjunto de comparação. O valor antigo incorreto não pode bloquear a própria retificação. Recalcular os limites usando a nova data quando fueledAt mudar.
  4. Calcular limite inferior pelas leituras anteriores (maior km) e superior pelas posteriores (menor km). Sem anterior, somente limite mínimo zero; sem posterior, não existe limite superior artificial. Leituras no mesmo instante exigem km igual. Limites incompatíveis ou quilometragem legada sem instante real geram conflito 409 orientando revisão do histórico, sem alterar dados.
  5. Aceitar limiteInferior ≤ odometerKm ≤ limiteSuperior. Retornar 422 ao violar uma fronteira, com mensagem que indica a quilometragem/data impeditiva sem revelar dados pessoais.

Consultas e fontes ficam em métodos dedicados do FuelingsRepository; a decisão de aceitar/rejeitar pertence ao FuelingsService. A consulta ao histórico legado é leitura de compatibilidade, não migração retroativa. As tabelas trip.trips têm start_km/end_km: não basta consultar exclusivamente abastecimentos.

5.5 Transação, concorrência e idempotência

  1. Validar forma, tipos, chave UUID e normalizar a entrada. Normalizar datas e decimais antes de comparar reenvios; preservar a diferença entre campo omitido e null no PUT.
  2. Consultar request_key por autor. Em reenvio equivalente, devolver a versão original antes de rejeitar expectedRevision obsoleta; mesma chave com outra operação, alvo ou conteúdo retorna 409.
  3. Abrir withTransaction; obter lock de fleet.vehicles por findByIdForUpdate; no PUT, reler e bloquear também a versão alvo. Manter a ordem veículo → abastecimento em todas as mutações.
  4. Reconsultar a chave após o lock; validar existência, revisão, ausência de sucessor, snapshots e cronologia dentro da transação. Não fazer checagem de km apenas antes de obter a trava.
  5. Gravar versão, leitura, evento e AuditService.recordAudit(..., client); commit somente depois de todos. finally libera conexão. Nenhuma chamada externa ocorre sob lock.
  6. O índice único por autor/chave cobre corridas entre veículos diferentes; em violação 23505, fazer rollback antes de reler a chave e distinguir replay de conflito. O índice de sucessor impede duas retificações do mesmo alvo.

A API de viagens ainda não está implementada nesta base. Os escritores futuros de hodômetro devem adquirir a mesma trava do veículo; documentar esse requisito de integração. Nesta entrega, testar concorrência com um escritor simulado que usa o mesmo protocolo. Não alegar garantia contra SQL externo ou escritores futuros que ignorem o lock.

5.6 Responsabilidades e erros

12. Princípios de Desenvolvimento e Restrições de Implementação

Aplicar a ordem de precedência da skill canônica principios:

  1. Padrões do projeto: Routes → Controllers → Services → Repositories; injeção leve; pg; schemas nativos; nomes de código em inglês e documentação em português.
  2. Escopo de impacto: somente API/testes de abastecimentos; GESTOR/ADMINISTRADOR; sem FROTA-66.
  3. Compatibilidade: preservar registros antigos, snapshots e formatos existentes; documentar claramente o novo contrato de retificação.
  4. Idempotência e atomicidade: mesma chave não duplica; trava por veículo; fato, leitura, evento e auditoria no mesmo commit.
  5. YAGNI: sem integração Prime, tela, cancelamento, novos serviços ou configurações.
  6. DRY: reusar transação, autoria, autenticação, autorização, auditoria e infraestrutura de testes.
  7. SOLID: I/O isolado, Service independente de Express e contratos enxutos.
  8. KISS: extensão localizada; sem framework de eventos, ORM ou abstrações genéricas novas.
  9. Clean Code: TypeScript estrito, retorno explícito, constantes e TSDoc semântico conforme docs/manuais/padroes-docblocks.md.

1. Contexto, Objetivo e Escopo

1.1 Contexto Operacional (FSPH / SVO)

O Sistema Aratu gerencia o transporte institucional de saúde da Fundação de Saúde Parreiras Horta (FSPH) e as operações sigilosas de coleta e entrega cadavérica do Serviço de Verificação de Óbito (SVO). A rastreabilidade operacional, a segregação de funções e a auditoria imutável (audit.logs) dependem de uma gestão robusta de identidades, perfis de acesso e permissões granulares.

1.2 Objetivo da Tarefa (Escopo Unificado de Infraestrutura de Acesso e RBAC)

Por decisão técnica e arquitetural alinhada com o desenvolvedor (Opção B), este plano unifica a entrega da tarefa-mãe de infraestrutura FROTA-156 e de suas duas únicas subtarefas — FROTA-30 (tabela de usuários) e FROTA-164 (tabelas de perfis, permissões e seed) —, antecipando e atendendo integralmente os critérios de pronto de backend da FROTA-37 (US03 / RBAC dinâmico e endpoint GET /profiles):

  1. Estrutura Relacional de Perfis e Permissões (RBAC Dinâmico): Criação das tabelas normalizadas auth.roles (perfis de acesso), auth.permissions (permissões atômicas de negócio) e auth.role_permissions (tabela de associação N:N entre perfis e permissões).
  2. Evolução da Tabela auth.users: Migração segura substituindo a restrição textual engessada pela chave estrangeira role_id BIGINT NOT NULL REFERENCES auth.roles(id) ON DELETE RESTRICT e inclusão da coluna de carimbo temporal updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp().
  3. Automação de Migrações (npm run db:migrate): Criação do script CLI backend/src/database/scripts/migrate.ts associado ao backend/package.json, executando o DatabaseMigrator de forma transacional e idempotente.
  4. Provisionamento Completo e Idempotente (npm run db:seed): Criação do script backend/src/database/scripts/seed.ts para:
    • Popular os 6 perfis canônicos do Aratu (ADMINISTRADOR, GESTOR, SOLICITANTE, MOTORISTA, ATENDENTE_SVO, EQUIPE_SVO) em auth.roles;
    • Registrar o catálogo inicial de permissões de negócio em auth.permissions;
    • Vincular permissões aos perfis correspondentes em auth.role_permissions;
    • Registrar o Administrador inicial em auth.users com role_id correspondente e senha hasheada com bcrypt via variáveis do .env (INITIAL_ADMIN_EMAIL, INITIAL_ADMIN_PASSWORD, INITIAL_ADMIN_NAME).
  5. Repositórios de Domínio:
    • UsersRepository: métodos tipados findByEmail (projetando dados de login e nome do papel via JOIN), findById, list (com filtros por roleId, active, termo de busca e paginação sargável), create e update;
    • RolesRepository: métodos findAll, findById e findPermissionsByRoleId.
  6. Contrato REST de Perfis (GET /profiles): Disponibilização do endpoint de listagem de perfis exigido pela FROTA-37 para alimentar os selects do frontend, protegido por token JWT e perfil ADMINISTRADOR via middleware authorizeRoles.
  7. Sigilo e Proteção de Credenciais: Garantir que nenhuma consulta de usuário exponha password_hash, exceto a consulta estrita de autenticação consumida pelo AuthService.

2. Requisitos e Regras de Negócio (Casos de Borda)

2.1 Requisitos Funcionais (RF)

  • RF01 (Migração SQL de RBAC Dinâmico e Usuários): Criar o arquivo de migração backend/src/database/migrations/202610180001_create_roles_permissions_and_update_users.sql e o rollback correspondente .down.sql, realizando em transação atômica:
    • Criação da tabela auth.roles com colunas id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name TEXT NOT NULL UNIQUE, description TEXT e created_at TIMESTAMPTZ;
    • Criação da tabela auth.permissions com colunas id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name TEXT NOT NULL UNIQUE, description TEXT NOT NULL e created_at TIMESTAMPTZ;
    • Criação da tabela de associação auth.role_permissions com id BIGINT IDENTITY PRIMARY KEY, role_id BIGINT REFERENCES auth.roles(id) ON DELETE CASCADE, permission_id BIGINT REFERENCES auth.permissions(id) ON DELETE CASCADE e constraint de unicidade (role_id, permission_id);
    • Evolução de auth.users: adição da coluna updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(), criação de role_id BIGINT NOT NULL REFERENCES auth.roles(id) ON DELETE RESTRICT e remoção da coluna legada role com preservação dos dados existentes.
  • RF02 (Comando de Migração): Implementar o script CLI backend/src/database/scripts/migrate.ts associado ao comando npm run db:migrate no backend/package.json, invocando DatabaseMigrator.runMigrations() com reporte de status.
  • RF03 (Seed Completo e Idempotente de RBAC e Administrador): Implementar o script CLI backend/src/database/scripts/seed.ts associado ao comando npm run db:seed no backend/package.json, realizando:
    • Provisionamento dos 6 perfis canônicos em auth.roles (ADMINISTRADOR, GESTOR, SOLICITANTE, MOTORISTA, ATENDENTE_SVO, EQUIPE_SVO);
    • Cadastro das permissões atômicas básicas do Aratu em auth.permissions;
    • Vinculação das permissões aos perfis em auth.role_permissions;
    • Criação do usuário com papel ADMINISTRADOR em auth.users apontando para o role_id do Administrador, com senha hasheada com bcrypt a partir de INITIAL_ADMIN_PASSWORD.
  • RF04 (Idempotência Estrita dos Seeds): Todas as etapas do seed devem ser 100% idempotentes, utilizando cláusulas ON CONFLICT DO NOTHING ou checagens preventivas por nome/e-mail para evitar duplicações ou falhas em reexecuções.
  • RF05 (Repositório de Perfis — RolesRepository): Implementar backend/src/repositories/roles.repository.ts com métodos:
    • findAll(): Promise<Role[]> — listagem de todos os perfis ativos para preenchimento de seletores;
    • findById(id: string): Promise<Role | null> — busca de perfil por ID;
    • findPermissionsByRoleId(roleId: string): Promise<Permission[]> — recuperação das permissões ativas atribuídas ao perfil.
  • RF06 (Repositório de Usuários — UsersRepository): Implementar backend/src/repositories/users.repository.ts com:
    • findByEmail(email: string): Promise<UserForLogin | null> — busca por e-mail com JOIN auth.roles projetando role para o contrato de login;
    • findById(id: string): Promise<User | null> — busca por ID com JOIN auth.roles projetando User (sem password_hash);
    • list(filters: UserFilters): Promise<PaginatedUsers> — listagem com filtros opcionais por roleId, active, busca textual e paginação sargável;
    • create(input: CreateUserInput, client?: PoolClient): Promise<User> — inserção com role_id, retornando entidade pública limpa;
    • update(id: string, input: UpdateUserInput, client?: PoolClient): Promise<UpdateUserResult> — atualização parcial condicionada a expectedRevision; incrementa revision, atualiza updated_at e distingue usuário inexistente de conflito de concorrência.
  • RF07 (Sigilo Estrito de Credenciais): Nenhuma operação em repositórios ou endpoints pode expor o campo password_hash, exceto a consulta restrita de autenticação consumida por AuthService.
  • RF08 (Middleware RBAC e Endpoint GET /profiles):
    • Implementar o middleware authorizeRoles(allowedRoles: UserRole[]) em backend/src/middlewares/rbac.middleware.ts;
    • Implementar ProfileService.listProfiles() entre o controller e RolesRepository, preservando a separação Controller → Service → Repository;
    • Disponibilizar a rota GET /profiles protegida por createAuthMiddleware e authorizeRoles(['ADMINISTRADOR']), retornando a lista de perfis no formato JSON [{ id, name, description }].

2.2 Requisitos Não-Funcionais (RNF)

  • RNF01 (Segurança contra SQL Injection): 100% das consultas executadas utilizam parâmetros posicionais ($1, $2, ...).
  • RNF02 (Consultas Sargáveis e Índices): Uso de lower(email) = $1 com índice auth_users_email_lower_unique e índices em chaves estrangeiras role_id e permission_id.
  • RNF03 (Criptografia Forte de Senhas): Hashing bcrypt (custo 12) via PasswordService::hashPassword com verificação em tempo constante contra truncamento (72 bytes).
  • RNF04 (Atomicidade e Transacionalidade): Migrações DDL e rotinas compostas rodam em blocos BEGIN ... COMMIT / ROLLBACK.
  • RNF05 (TypeScript Estrito): Ausência total de any e tipagens dedicadas para Role, Permission e User.
  • RNF06 (Proteção LGPD e Sigilo SVO): Utilização exclusiva de dados puramente sintéticos nos exemplos e testes automatizados.
  • RNF07 (Padronização de SQL): Nos arquivos de backend desta entrega, consultas usam projeções reutilizáveis sem credenciais, cláusulas SQL em maiúsculas, parâmetros posicionais e montagem dinâmica limitada a fragmentos controlados pelo repositório.
  • RNF08 (Concorrência Otimista): Atualizações de usuário exigem expectedRevision e retornam resultado discriminado para que a borda HTTP futura converta conflito em 409 Conflict.

2.3 Regras de Negócio e Casos de Borda

Cenário / Regra Condição de Entrada Comportamento Esperado / Resolução de Borda
Normalização de E-mail E-mail informado com espaços no início/fim ou letras maiúsculas (ex: " Admin@FSPH.SE.GOV.BR "). O repositório e os scripts aplicam trim().toLowerCase() antes de persistir ou consultar no banco, garantindo que o índice lower(email) opere de forma consistente.
Tentativa de E-mail Duplicado Tentativa de cadastrar usuário com e-mail já existente (ex: admin@fsph.se.gov.br). O banco aciona a constraint auth_users_email_lower_unique disparando erro PostgreSQL 23505 (unique_violation). O chamador recebe a rejeição sem violar a unicidade.
Integridade Referencial de Perfil Tentativa de cadastrar ou atualizar usuário informando um role_id inexistente. A constraint auth.users_role_id_fkey rejeita a operação com erro PostgreSQL 23503 (foreign_key_violation).
Exclusão de Perfil em Uso Tentativa de deletar um registro em auth.roles associado a contas ativas. A cláusula ON DELETE RESTRICT bloqueia a exclusão para evitar orfandade de permissões.
Reexecução de Seed em Base Existente O comando npm run db:seed é executado em um banco onde perfis e o administrador já existem. O script reconhece os registros existentes via ON CONFLICT DO NOTHING e encerra com log informativo, finalizando com código 0 (sucesso).
Acesso ao Endpoint GET /profiles sem Autorização Usuário com perfil MOTORISTA ou SOLICITANTE tenta acessar GET /profiles. O middleware authorizeRoles intercepta a requisição e responde HTTP 403 Forbidden com mensagem: "Acesso negado: perfil não autorizado para esta operação."
Atualização Parcial de Usuário Chamada a UsersRepository.update(id, { name: 'Novo Nome', expectedRevision: 1 }) sem alterar senha ou role_id. Apenas os campos fornecidos são alterados quando a revisão esperada coincide; o UPDATE incrementa revision e atualiza updated_at.
Conflito de Atualização Concorrente Cliente tenta alterar usuário com expectedRevision inferior à revisão persistida. O repositório retorna { kind: 'revision-conflict' }; futuro controller traduz o resultado em HTTP 409 Conflict.

2.4 Cenários Comportamentais (Dado / Quando / Então)

Cenário 1: Migração em Banco Vazio e Execução de Seed Completo

Dado um banco PostgreSQL 18 vazio sem tabelas de domínio;
Quando o operador executa npm run db:migrate seguido de npm run db:seed;
Então as tabelas auth.roles, auth.permissions, auth.role_permissions e auth.users são provisionadas e o administrador inicial é criado vinculado ao perfil ADMINISTRADOR com senha hasheada por bcrypt.

Cenário 2: Primeiro Login do Administrador Criado pelo Seed

Dado o administrador inicial provisionado pelo seed com a senha definida em INITIAL_ADMIN_PASSWORD;
Quando uma requisição POST /auth/login é enviada com o e-mail e a senha em texto claro;
Então o AuthService valida a credencial via comparePassword, realiza o JOIN em auth.roles e emite o token JWT assinado com perfil ADMINISTRADOR.

Cenário 3: Consulta de Perfis por Administrador Autorizado (FROTA-37)

Dado um token JWT válido pertencente a um usuário com perfil ADMINISTRADOR;
Quando uma requisição GET /profiles for enviada;
Então o endpoint retorna status HTTP 200 OK com o array de todos os perfis disponíveis (id, name, description) para alimentar os componentes de formulário do frontend.

Cenário 4: Bloqueio de Acesso a Perfis por Perfil Não Autorizado

Dado um token JWT válido de usuário com perfil MOTORISTA;
Quando a requisição GET /profiles for enviada;
Então o middleware authorizeRoles bloqueia a execução e devolve status HTTP 403 Forbidden.

4. Banco de Dados e Migrações (PostgreSQL 18)

4.1 DDL Transacional da Migração (Up)

Arquivo: backend/src/database/migrations/202610180001_create_roles_permissions_and_update_users.sql 

BEGIN;

-- 1. Criar tabela de perfis de acesso (auth.roles)
CREATE TABLE IF NOT EXISTS auth.roles (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL CHECK (btrim(name) <> ''),
  description TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE UNIQUE INDEX IF NOT EXISTS auth_roles_name_unique ON auth.roles (upper(name));

-- 2. Popular os 6 perfis canônicos na migração para suportar a FK de usuários imediatamente
INSERT INTO auth.roles (name, description) VALUES
  ('ADMINISTRADOR', 'Acesso global de parametrização e administração do sistema'),
  ('GESTOR', 'Gestão operacional de frotas, condutores e aprovação de viagens FSPH'),
  ('SOLICITANTE', 'Abertura e acompanhamento de requisições de transporte institucional'),
  ('MOTORISTA', 'Acesso a viagens atribuídas e registro de hodômetro/execução'),
  ('ATENDENTE_SVO', 'Recepção, triagem de chamados e solicitação de remoção cadavérica'),
  ('EQUIPE_SVO', 'Atendimento operacional sigiloso, coleta e entrega cadavérica no SVO')
ON CONFLICT DO NOTHING;

-- 3. Criar tabela de permissões granulares (auth.permissions)
CREATE TABLE IF NOT EXISTS auth.permissions (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL CHECK (btrim(name) <> ''),
  description TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE UNIQUE INDEX IF NOT EXISTS auth_permissions_name_unique ON auth.permissions (lower(name));

-- 4. Criar tabela associativa N:N entre perfis e permissões (auth.role_permissions)
CREATE TABLE IF NOT EXISTS auth.role_permissions (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  role_id BIGINT NOT NULL REFERENCES auth.roles(id) ON DELETE CASCADE,
  permission_id BIGINT NOT NULL REFERENCES auth.permissions(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  CONSTRAINT auth_role_permissions_unique UNIQUE (role_id, permission_id)
);

CREATE INDEX IF NOT EXISTS auth_role_permissions_by_role ON auth.role_permissions (role_id);
CREATE INDEX IF NOT EXISTS auth_role_permissions_by_permission ON auth.role_permissions (permission_id);

-- 5. Atualizar tabela auth.users: adicionar updated_at e migrar role para role_id
ALTER TABLE auth.users
  ADD COLUMN IF NOT EXISTS updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  ADD COLUMN IF NOT EXISTS role_id BIGINT REFERENCES auth.roles(id) ON DELETE RESTRICT;

-- Se a tabela já contiver linhas com role textual, migrar para role_id
UPDATE auth.users u
   SET role_id = r.id
  FROM auth.roles r
 WHERE u.role_id IS NULL AND upper(r.name) = upper(u.role);

-- Tornar role_id obrigatório e remover coluna textual legada
ALTER TABLE auth.users
  ALTER COLUMN role_id SET NOT NULL;

ALTER TABLE auth.users
  DROP COLUMN IF EXISTS role;

CREATE INDEX IF NOT EXISTS auth_users_by_role ON auth.users (role_id);

COMMIT;

4.2 DDL de Rollback (Down)

Arquivo: backend/src/database/migrations/202610180001_create_roles_permissions_and_update_users.down.sql 

BEGIN;

-- 1. Restaurar coluna role textual com as invariantes originais
ALTER TABLE auth.users
  ADD COLUMN IF NOT EXISTS role TEXT;

UPDATE auth.users u
   SET role = r.name
  FROM auth.roles r
 WHERE u.role_id = r.id;

ALTER TABLE auth.users
  ALTER COLUMN role SET NOT NULL;

ALTER TABLE auth.users
  DROP CONSTRAINT IF EXISTS auth_users_role_check,
  ADD CONSTRAINT auth_users_role_check CHECK (role IN (
    'ADMINISTRADOR',
    'GESTOR',
    'SOLICITANTE',
    'MOTORISTA',
    'ATENDENTE_SVO',
    'EQUIPE_SVO'
  ));

-- 2. Remover constraints e colunas novas de auth.users
DROP INDEX IF EXISTS auth.auth_users_by_role;
ALTER TABLE auth.users
  DROP CONSTRAINT IF EXISTS auth_users_role_id_fkey,
  DROP COLUMN IF EXISTS role_id,
  DROP COLUMN IF EXISTS updated_at;

-- 3. Remover tabelas associativas e de perfis
DROP TABLE IF EXISTS auth.role_permissions;
DROP TABLE IF EXISTS auth.permissions;
DROP TABLE IF EXISTS auth.roles;

4.3 Modelo Estrutural das Tabelas do Schema auth

4.4 Índices e Integridade Referencial

  • auth_users_email_lower_unique ON auth.users (lower(email)): Unicidade e busca acelerada em login;
  • auth_users_by_role ON auth.users (role_id): Acelera filtros por perfil na listagem de usuários e integridade da FK;
  • auth_roles_name_unique ON auth.roles (upper(name)): Impede duplicidade de nomes de perfis;
  • auth_permissions_name_unique ON auth.permissions (lower(name)): Garante unicidade de identificadores de permissão;
  • auth_role_permissions_unique ON auth.role_permissions (role_id, permission_id): Garante associação N:N sem duplicação;
  • user_id REFERENCES auth.users(id) ON DELETE RESTRICT em audit.logs: Preserva a rastreabilidade imutável de auditoria.

5.2 Repositório de Perfis (backend/src/repositories/roles.repository.ts)

Contrato RoleRepositoryContract e classe RolesRepository para persistência e recuperação de perfis e permissões granulares: 

import type { Pool, PoolClient } from 'pg';
import type { Role, Permission, UserRole } from '../types/auth';

export interface RoleRepositoryContract {
  findAll(client?: PoolClient): Promise<Role[]>;
  findById(id: string, client?: PoolClient): Promise<Role | null>;
  findByName(name: UserRole, client?: PoolClient): Promise<Role | null>;
  findPermissionsByRoleId(roleId: string, client?: PoolClient): Promise<Permission[]>;
}

export class RolesRepository implements RoleRepositoryContract {
  constructor(private readonly pool: Pool) {}

  async findAll(client?: PoolClient): Promise<Role[]> {
    const executor = client ?? this.pool;
    const { rows } = await executor.query<Role>(`
      SELECT id::text AS id, name, description, created_at AS "createdAt"
        FROM auth.roles
       ORDER BY id ASC;
    `);
    return rows;
  }

  async findById(id: string, client?: PoolClient): Promise<Role | null> {
    const executor = client ?? this.pool;
    const { rows } = await executor.query<Role>(`
      SELECT id::text AS id, name, description, created_at AS "createdAt"
        FROM auth.roles
       WHERE id = $1
       LIMIT 1;
    `, [id]);
    return rows[0] ?? null;
  }

  async findByName(name: UserRole, client?: PoolClient): Promise<Role | null> {
    const executor = client ?? this.pool;
    const { rows } = await executor.query<Role>(`
      SELECT id::text AS id, name, description, created_at AS "createdAt"
        FROM auth.roles
       WHERE upper(name) = upper($1)
       LIMIT 1;
    `, [name]);
    return rows[0] ?? null;
  }

  async findPermissionsByRoleId(roleId: string, client?: PoolClient): Promise<Permission[]> {
    const executor = client ?? this.pool;
    const { rows } = await executor.query<Permission>(`
      SELECT p.id::text AS id, p.name, p.description, p.created_at AS "createdAt"
        FROM auth.permissions p
        JOIN auth.role_permissions rp ON rp.permission_id = p.id
       WHERE rp.role_id = $1
       ORDER BY p.name ASC;
    `, [roleId]);
    return rows;
  }
}

5.4 Middleware de Autorização RBAC (backend/src/middlewares/rbac.middleware.ts)

Interceptador desacoplado para validação de perfis autorizados (Chain of Responsibility): 

import type { Request, Response, NextFunction } from 'express';
import type { UserRole } from '../types/auth';

/**
 * Middleware de autorização que restringe o acesso a determinados perfis RBAC do Aratu.
 *
 * @param allowedRoles - Lista de papéis permitidos a executar a rota.
 * @returns Middleware Express que avalia req.usuario.perfil.
 */
export function authorizeRoles(allowedRoles: readonly UserRole[]) {
  return (req: Request, res: Response, next: NextFunction): void => {
    const userRole = req.usuario?.perfil as UserRole | undefined;

    if (!userRole || !allowedRoles.includes(userRole)) {
      res.status(403).json({
        erro: 'Acesso negado: perfil de usuário não autorizado para esta operação.',
      });
      return;
    }

    next();
  };
}

B. Script backend/src/database/scripts/seed.ts (npm run db:seed)

import dotenv from 'dotenv';
import path from 'node:path';
import { createPool } from '../pool';
import { UsersRepository } from '../../repositories/users.repository';
import { RolesRepository } from '../../repositories/roles.repository';
import { hashPassword } from '../../services/password.service';

dotenv.config({ path: path.resolve(__dirname, '../../../../.env') });
dotenv.config({ path: path.resolve(__dirname, '../../../.env') });

async function runSeed(): Promise<void> {
  const databaseUrl = process.env.DATABASE_URL;
  const adminEmail = process.env.INITIAL_ADMIN_EMAIL?.trim().toLowerCase();
  const adminPassword = process.env.INITIAL_ADMIN_PASSWORD;
  const adminName = process.env.INITIAL_ADMIN_NAME?.trim() || 'Administrador do Sistema';

  if (!databaseUrl) {
    process.stderr.write('Erro: DATABASE_URL é obrigatória para o seed.\n');
    process.exit(1);
  }

  if (!adminEmail || !adminPassword) {
    process.stderr.write('Erro: Defina INITIAL_ADMIN_EMAIL e INITIAL_ADMIN_PASSWORD no .env para o seed.\n');
    process.exit(1);
  }

  const pool = createPool(databaseUrl);
  const userRepo = new UsersRepository(pool);
  const roleRepo = new RolesRepository(pool);

  try {
    // 1. Garantir existência do perfil ADMINISTRADOR
    const adminRole = await roleRepo.findByName('ADMINISTRADOR');
    if (!adminRole) {
      process.stderr.write('Erro: Perfil ADMINISTRADOR não encontrado. Execute npm run db:migrate antes do seed.\n');
      process.exit(1);
    }

    // 2. Verificar idempotência do usuário administrador
    const existing = await userRepo.findByEmail(adminEmail);
    if (existing) {
      process.stdout.write(`Seed: Administrador "${adminEmail}" já existe na base. Inserção ignorada.\n`);
      return;
    }

    // 3. Cadastrar Administrador inicial com role_id
    const passwordHash = await hashPassword(adminPassword);
    const createdUser = await userRepo.create({
      name: adminName,
      email: adminEmail,
      passwordHash,
      roleId: adminRole.id,
      active: true,
    });

    process.stdout.write(`Seed: Administrador inicial criado com sucesso (ID: ${createdUser.id}, Email: ${createdUser.email}, Perfil: ${adminRole.name}).\n`);
  } finally {
    await pool.end();
  }
}

void runSeed().catch((err: unknown) => {
  process.stderr.write(`Falha fatal no seed de usuários: ${String(err)}\n`);
  process.exit(1);
});

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.

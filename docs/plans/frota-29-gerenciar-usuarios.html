1. Contexto, Objetivo e Escopo

Objetivo: permitir que o Administrador da FSPH/SVO cadastre, consulte, filtre, edite, inative e reative contas de usuários, controlando o acesso ao sistema e preservando o histórico (sem exclusão física).

Problema atual: a tela UserManagementPage.tsx existe apenas como esqueleto visual, sem consumir /users; o Administrador não consegue operar o cadastro.

1.1 Delimitação de Escopo (YAGNI)

  • Entra no escopo: API /users (FROTA-31), testes automatizados (FROTA-34), integração da tela já criada (FROTA-32), item de menu exclusivo do Administrador, auditoria em audit.logs.
  • Fora do escopo: DELETE /users; recuperação/alteração de senha; envio de e-mail; importação de usuários; exportação; paginação por keyset; busca com pg_trgm; refatoração ampla da tela para components/ui; gestão de perfis/permissões (FROTA-35).

1.2 Decisões Confirmadas (Regra da Dúvida)

  • Senha inicial definida pelo Administrador no cadastro (campo já existente na tela).
  • GET /users responde envelope paginado { users, total, page, pageSize, totalPages }.
  • PUT /users/:id exige revision no corpo (controle otimista, 409 em conflito).
  • Testes com node:test + fetch, reutilizando a infraestrutura existente, sem supertest.
  • Senha validada apenas como não vazia e com até 72 bytes UTF-8 (limite do bcrypt).

2. Requisitos e Regras de Negócio (Casos de Borda)

2.1 Requisitos Funcionais

IDRequisito
RF01GET /users lista com filtros opcionais nome, perfil, ativo e paginação.
RF02GET /users/:id retorna detalhe; inexistente → 404.
RF03POST /users cadastra nome, e-mail, perfil, situação e senha inicial; responde 201.
RF04PUT /users/:id edita nome, e-mail e perfil com revision obrigatória.
RF05PATCH /users/:id/deactivate e /activate inativam e reativam.
RF06Administrador não pode inativar a própria conta.
RF07Nenhuma resposta devolve password_hash.
RF08Cadastro, edição, inativação e reativação são auditados em audit.logs.

2.2 Regras e Casos de Borda

  • Nome: obrigatório, trim não vazio → 400.
  • E-mail: obrigatório, formato nome@dominio.com, normalizado para minúsculas; duplicado → 409 “E-mail já cadastrado.”.
  • Perfil: obrigatório e existente em auth.roles → inválido 400.
  • Senha inicial: obrigatória no cadastro, não vazia e ≤ 72 bytes; hash bcrypt custo 12.
  • Situação: active booleano, padrão true.
  • Autoinativação: 409 “Você não pode inativar a própria conta.”.
  • Idempotência: inativar já inativo ou ativar já ativo → 200 sem novo evento de auditoria.
  • Concorrência: revision divergente → 409; leitura/gravação com SELECT ... FOR UPDATE.
  • Inexistente: 404 “Usuário não encontrado.”; ID não numérico → 400.

2.3 Cenários Dado / Quando / Então

  • Dado um admin autenticado, quando cadastra e-mail novo, então recebe 201 sem password_hash.
  • Dado e-mail existente, quando cadastra, então recebe 409.
  • Dado usuário ativo, quando inativado, então o login retorna 403 “Acesso desativado”.
  • Dado usuário inativo, quando reativado, então o login volta a funcionar.
  • Dado o próprio admin, quando tenta se inativar, então a operação é bloqueada.
  • Dado um GESTOR, quando acessa /users, então recebe 403.

2.4 Requisitos Não Funcionais

  • Queries parametrizadas ($1, $2), sem SELECT *.
  • Escritas em transação com SELECT ... FOR UPDATE e client.release() no finally.
  • Mensagens em português claro na chave erro.
  • Dados de teste 100% fictícios (LGPD) e conformidade WCAG 2.2 AA na tela.

4. Banco de Dados e Migrações (PostgreSQL 18)

Não se aplica a esta tarefa. Nenhuma migração é necessária: auth.users já possui id, name, email, password_hash, role_id, active, revision, created_at, updated_at, FK role_id → auth.roles(id) ON DELETE RESTRICT e o índice único auth_users_email_lower_unique ON auth.users (lower(email)).

Plano de Rollback: não há DDL a reverter. Alterações futuras devem vir em migração transacional própria (BEGIN ... COMMIT) com arquivo .down.sql.

Performance: a busca parcial por nome usa lower(name) LIKE '%termo%', sem índice B-tree. Para o volume atual, é aceitável; qualquer índice futuro deve ser justificado por EXPLAIN (YAGNI).

5.3 Camadas

  • Controller: lê req.query/req.body, converte ativo para booleano, chama o service e responde { erro } em UserServiceError; demais erros seguem para o handler global.
  • Service puro: listUsers, getUser, createUser, updateUser, deactivateUser, activateUser. Sem Express, sem SQL.
  • Repository: withTransaction, findByIdForUpdate (SELECT ... FOR UPDATE), list existente e update condicionado por revision com suporte a email.
  • Rotas: authenticate → authorizeRoles(['ADMINISTRADOR']) → controller (Chain of Responsibility).
  • Auditoria: AuditService.recordAudit na mesma transação, com before/after/actorSnapshot e operações CREATE, UPDATE e STATUS_CHANGE.
  • Erros: 23505 do PostgreSQL convertido em 409 de e-mail duplicado.

12. Princípios de Desenvolvimento e Restrições de Implementação

Seção obrigatória em todo plano técnico do Sistema Aratu (conforme .agents/skills/principios/references/planejamento.md).

A implementação deste plano segue estritamente a ordem de precedência da skill canônica principios:

  1. Padrões do Projeto Aratu: camadas Node.js/Express 5 (routes → controllers → services → repositories), Padrões de Projeto conforme docs/manuais/padroes-projeto.md, React 19 (pages, components/ui, services) e PostgreSQL 18 em Schemas Nativos de Domínio em inglês (auth, fleet, trip, svo, audit).
  2. Escopo de Impacto: controle por dado de domínio e perfis RBAC (ADMIN, MANAGER, OPERATOR, REQUESTER, TRIAGE, DRIVER).
  3. Compatibilidade de Dados e Contratos: preservação dos contratos JSON e integridade dos registros já gravados.
  4. Idempotência e Atomicidade: transações explícitas no pool pg com SELECT ... FOR UPDATE em alocações concorrentes.
  5. YAGNI: sem parâmetros, tabelas ou abstrações especulativas.
  6. DRY: regra de negócio em um único Service e componentes visuais reutilizados de components/ui/.
  7. SOLID e KISS: responsabilidade única, baixo acoplamento e solução mais simples e legível.
  8. Clean Code e TypeScript Estrito: código em inglês, zero any, zero valores mágicos, e TSDoc semântico em português conforme docs/manuais/padroes-docblocks.md.
  • Regra Inegociável da Dúvida na Implementação: Qualquer divergência encontrada entre este plano e a base de código real interrompe o trabalho e vira pergunta objetiva ao usuário. É terminantemente proibido improvisar ou assumir premissas.
  • Proteção de Dados (LGPD / SVO): Nenhum dado pessoal real de motoristas, servidores ou falecidos entra em seeds, testes, fixtures ou commits.
